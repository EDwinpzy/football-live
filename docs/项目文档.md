### 0.1 起播线路按实测健康度排序（2026-09-29，热更 v27）

**问题现场**：《肖申克的救赎》详情返回 12~13 条线路，App 从 line 0 逐条试到
line 12，每条精确等满 5s 首帧看门狗才换线，点播放到出画耗时 **78.8 秒**。

**两个根因**（缺一不可，只修一个都不够）：

1. **排序缺失**：`LineHistory` 一直在 `record(线路, 成功/失败)`，也有
   `success_rate()`，但全仓库没有任何地方读它排序——数据在攒，排序没用上。
   缓存命中路径走 `rank_lines()`，而实测命中的**实时匹配路径完全没排序**。
2. **云端解析打错地址**：`VodRepository.fetchResolve` 用的是
   `settings.hhkanBaseUrl`，默认值 `http://127.0.0.1:8090` —— App 自己的
   内嵌后端。于是 L1「云端预匹配」永远打不到服务端，每次播放都回落
   `local_detail`，拿回本地实时匹配的原始顺序。
   服务端能力其实是好的：`/vod/resolve/1291546?episode=1` 返回 `MATCHED`
   且带完整 `preferred`（猫眼，match_score 100）。

**改动**：

- `vod_sources.rank_lines_by_health(lines, history)`：按最近 20 次成功率排序，
  无历史记 0.5（中性，不打乱顺序）；最近连续失败额外扣分（最多 0.45），
  因为线路会坏——历史成功率很高但最近连挂的线必须排到未知线之后。
  排序稳定（分数相同保持原相对顺序，避免每次刷新顺序抖动导致缓存失效）；
  纯函数不改入参；`history=None` 原样返回。每条线带 `health_score` /
  `health_samples` 便于排障。
- `vod_api.VodService.detail()` 在写入 `subject["sources"]` **之前**调用排序
  （排序早于发布才有效），`_resolved_lines` 查表顺序也跟着一致。
- 两端新增 `CloudResolveBase.pick(settings)` 决定 L1 打哪个地址：
  Release 注入的 `apiBaseUrl`（远端）→构建期 `BuildConfig.API_BASE_URL`
  → 用户手动改过的远端 `hhkanBaseUrl` → 最后才回退内嵌后端保持离线可用。
  远端站点根自动补 `/web` 段（VPS 的 nginx 只把 web 前缀转给 web-api，
  站点根下的 vod 路由是 404）；内嵌后端不能加前缀。

**实测证据（emulator-5554 / 5556，2026-09-29）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| TV 点播放→出画 | 78.8s（试 12 条线） | **7.7s**（line 0 猫眼 5s 未出 → 切 line 1） |
| 移动端点播放→出画 | — | **4.8s**（`线路1/1`，line 0 直接可用，未触发换线） |
| L1 云端预匹配 | 每次回落 `local_detail` | `resolve_first_source tier=cloud_preferred`，274ms |
| 详情接口排序字段 | 无 | `health_score=0.5` `health_samples=0`（线上实测） |

截图证据：`artifacts/2026-09-startup-fix/`（`tv-play-final.png` 真实画面渲染、
`mobile-playing2.png` 移动端播放中含倍速/画幅/投屏面板）。

**测试**：`tools/backend-src/tests/test_line_health_ranking.py`（8 项，

## 1. 产品概览

**My TV（OptimalTV 工程）**：Android 原生影视应用（TV 大屏 + 手机/平板双端）+ Windows 桌面版 + 云端网页版，
Kotlin + Jetpack Compose + Media3，tvOS 深色风格。影片卡片、详情和筛选以豆瓣目录为准，
播放线路来自后台可管理的现有影视源。**后端打包进 app**（Chaquopy 内嵌 Python），
每台设备直接访问公网内容源与播放源。商业化 = 卡密付费（公测版门控）。

### 发布边界

- 本机是唯一代码整理、构建和 Git 发布入口。
- 后端与 `www/` 使用同一份内容寻址 zip，在后台静默下载、SHA-256 + 结构校验后只重启
  `:backend` 进程，App 前端不弹窗。
- Kotlin / Compose 等原生 UI 无法由 Python zip 替换，必须构建签名 APK 交给 Android 系统安装器更新。
- 足球队标使用「内置映射优先 → football-logos.cc 在线补全 → 磁盘缓存 → TheSportsDB → 文字兜底」。
  按非商业粉丝项目使用该站资源，不把全量队标打包进 APK；后端保存已解析结果，站点不可用时仍保留回退链。

### 产品矩阵（2 APK + 1 EXE + 1 网页）

| 产物 | 工程/位置 | 包名 | 状态 |
|---|---|---|---|
| TV 版 | `android/` | `com.qiubo.optimaltv.public` | 全量功能 + 卡密门控；投屏已整体移除 |
| 移动版 | `internal/mobile/` | `com.qiubo.optimaltv.mobile.public` | 与 TV 共享 data/playback/backend，触屏 UI，保留 DLNA 投屏 |
| Windows 版 | `desktop/` | `apk/Windows版/MyTV.exe` | WebView2 桌面窗口 + 本机 Python 后端；前端、快照与 HLS 脚本内置 |
| 网页版 | VPS 容器 `web-api`（源码 `tools/backend-src/`） | —（HTTPS 服务） | 入口 `https://<正式域名>/web/`（IP + 迁移 CA 仅本机 Debug 联调） |

### 核心能力一览

影视点播（首页/全部/详情选集/搜索/收藏/历史）· 卫视直播（精编频道表 + 多源备份无感切换）·
IPTV 电视（400+ 频道分组选台 + 足球直播广场）· 播放三级回退（Media3 → 中继 HLS → libVLC）·
DLNA 投屏（仅移动端）· 卡密付费（一码 2 台设备，网络异常宽限 24 小时）· 热更新（改后端不发 APK）·
后台管理（卡密/热更/公告/电视源/影视源动态管理）· 网页版（云端影视 + IPTV）· OtvNav 遥控器焦点引擎。

## 2. 总体架构

```
[TV 版 / 移动版 APK]       [Windows EXE]       [网页版浏览器]
  Chaquopy 内嵌 Python 后端 :8090   ┌─→  /web/（同一份 proxy.py，跑在 VPS 容器里）
  HotUpdateManager ← 热更包         │
  Windows 端：WebView2 → 本机 proxy.py（优先 127.0.0.1:8090）
        │                            │
        ▼                            ▼
  [自建 VPS 103.236.97.137（服务商 NAT：外 35208 → 内 8443）]
    Nginx 路由见 §7.2；容器清单见 §7.3
    仓库副本 /srv/mytv（不是 git 仓库，部署靠同步目录后 docker compose up -d --build）

  [腾讯云 CloudBase appletv-d5ge1bth794873f76]   ← 已退役，不再提供任何服务
    历史：09-15 自建站点（Sites/Worker）国内大面积 403 → 09-16 回迁 CloudBase → 09-23 迁到自建 VPS
    → 已下线（环境 / 兼容入口 / 对象镜像 / cloudfunctions 部署包全部删除）
```

- **内嵌后端**：`proxy.py` / `hhkan.py` / `hhkan_snapshot.py` + `hhkan_snapshot.json` /
  `scraper.py` / `douban_catalog.py` / `vod_resolver.py` / `team_backdrop.py` / `www/`
  打包为 `assets/backend/python-backend.zip`，app 启动解压运行于 `127.0.0.1:8090`。
  **这也是热更对象**——改抓取逻辑/换图源/改 UI 资源无需发新 APK。
- **:backend 独立进程**（v1.20）：`BackendService`（`android:process=":backend"`）承载 Chaquopy；
  热更生效 = service 内自杀重建（app 主进程全程在线）；后端状态经 `filesDir/hu_state.json`
  文件通道回传（DataStore 非多进程安全）。
- **兼容性基线**：minSdk 30（坚果 N1 Air / Android 11），零 GMS；ABI arm64/v7a + x86_64。
- **足球云端兜底**（2026-09-10）：家宽出口被 yoozb 系拉黑（403）时，设备端 `/api/matches`
  与 `/api/stream` 自动回退云端同代码接口；兜底响应 `source` 带 `|cloud-relay` 标记。
  环境变量 `OTV_CLOUD_RELAY` 控制，`OTV_CLOUD_BASE` 覆盖兜底地址。

## 3. 端侧功能模块

### 3.1 影视点播与搜索

- 目录/卡片/元数据以**豆瓣目录**为准（`douban_catalog.py`），搜索支持拼音输入法
  （AOSP 谷歌拼音解码器 `cpp/pinyinime`）与首字母联想（构建期两张 asset 表：
  `tools/gen_pinyin_initials.py` / `gen_pinyin_titles.py`）。
- **搜索覆盖与模糊匹配（2026-09-30）**：按通用检索链路修复，不按单个片名做特例。
  非空查询均合并本地索引与豆瓣影视搜索，已有部分结果不再挡住未收录作品；
  保留上游按简称、别名、译名命中的结果，不再用标题包含规则二次误过滤。
  精确匹配优先，其后保留上游相关性顺序，再补本地结果；分页按真实偏移返回。
  本地支持部分片名、拼音、首字母与轻微错字；去除打分前 500 条截断，弱匹配
  不再压制错字回退，外文重音与不带重音输入互查。旧数据库首次打开时自动迁移
  检索列，保留详情与 schema 版本，支持旧后端回滚读取。
  主接口超时 4 秒、成功缓存 30 分钟，真实空结果只缓存 60 秒；风控/网络失败
  独立冷却 60 秒，并尝试公开 subject_suggest（超时 2 秒、缓存 60 秒）。
  主接口空结果也允许备用补查，不因空结果缓存挡住备用；重复查询复用备用缓存。
  备用接口最多并行核对 8 条标准详情，每条超时 2 秒，不信其统一 movie 类型；
  两路均失败仍返回本地命中。备用摘要与详情都不可得的新条目不猜分类。
  搜索卡片只补齐旧记录缺失字段，保留完整简介/主创；明确类型信息可修正旧分类。
  随包搜索池加入《声生不息》六个季度，断网搜索 `声生`、`声生不息` 均返回六条；
  启动时给已有索引补入快照新增条目，重建快照保留历史搜索条目及详情。
  Web / TV / 移动版直接采用结果自带的豆瓣分类，补上「综艺」筛选入口；
  合并时后端结果优先，本地目录仅补充，避免旧副本覆盖新分类和相关性排序。
  Web 搜索卡片限制最小宽度，避免大尺寸海报把网格撑出屏幕。
  本地 Web 实测完整片名、部分片名及综艺筛选均显示六条；截图位于
  `artifacts/2026-09-search-evidence/`。在线缺失检索也用真实豆瓣接口验证了完整片名、

  pid≥100 使用站点命名空间，≥720p 线路优先供播放器自动选择。补线总开关 env `OTV_ENRICH=0` 可关闭。
- **片库筛选三态判定**：上游空壳响应不得当成空结果（降级链 + 冷却），上游不可用时走
  快照实测汇总 + 本地保守判定。分类 × 参数能力矩阵数据化
  （`tools/backend-src/douban_filter_matrix.json`，探测脚本 `tools/probe_douban_filter_matrix.py`），
  准确度自检 `tools/check_vod_filter_accuracy.py`。
  **无实测数据时一律本地判定——宁可少给，不给错。**
- **片库 LazyColumn 的 item key 必须用板块名**（`lib-sec-{sec.name}-r{ri}`）：
  三块到货顺序与 blockOrder 展示顺序不一致，序号 key 会让迟到板块插入触发全部行 item 重建
  → 聚焦节点销毁、焦点乱甩（TV 端「光标跳行」的根因）。TV 与移动版同款布局同规则。

### 3.2 卫视直播与 IPTV

- 卫视直播：精编频道表内置（assets `iptv_curated.m3u`），台标本地图标（`tools/build_logo_assets.py`
  生成，序号=已落盘最大+1 防串台；暗标白化 normalize_logo），自动补源、多源备份无感切换。
- IPTV 电视：SOURCES = 云端桶 latest（首位）+ Guovin（gh-proxy/jsdelivr）+ vbskycn；
  快照落 `files/iptv_snapshot.m3u` 先读秒上屏；刷新节流 ≤30min。
- 测速换台：`rankUrls()` TTFB 测速排序起播即最快线；BUFFERING>3.5s 且备线分值
  <0.55×当前 → 无感切换；侧边栏 60s 周期探测组内前 40 线路。
- 播放健壮性：首帧看门狗（READY 15s 无首帧→切 VLC）；fatalMsg 12s 未恢复自动跳台
  （环形，连续 3 次上限）；ac3/eac3/dts 音轨自动转 VLC。
- **SSRF 双层校验** `data/source/UrlGuard.kt`：仅 http/https、拒私网/环回/IPv4-mapped，
  `assertPublicResolved()` DNS 全 A 记录私网则拒；列表拉取侧 + 起播侧两层。

### 3.3 播放引擎

- 三级回退：Media3 硬解 → 中继 HLS → libVLC；点播直播共用会话代数管理（engineEpoch）。
- 直播 HLS 经本机中继（签名 ~9 分钟轮换 + 90s 续签热切换）；解密中继 `StreamDecryptServer`
  用 **3-WebView 解密池**（信号量 + 槽位并发，串行→3.2× 吞吐，替代单实例全局锁）。
- 足球解密三级分发：端内 QuickJS HTTP bridge（:8091）/ 本地 node / 云函数 `decrypt_python.py`。
- **解密池自愈**：`StreamDecryptServer` 的 WebView 加 `WebViewClient.onRenderProcessGone`
  → 销毁清槽懒重建；12s 零回调僵死检测兜底（渲染进程活着但页面级僵死的形态）；
  poll/loadData 全面 runCatching。根治「反复加载混淆页数小时后渲染进程崩溃 → 僵死 WebView 永久
  留池 → 每次解密 12s 超时 → 三槽全僵 =『半小时后所有信号源失效』」。

#### 直播长跑稳定性（2026-09-16）— 三个根因与对应修复

用户报「播十几二十分钟后画面冻住，退出重进才好」。供给侧实测是健康的：中继日志逐条统计分片请求，
序号无跳号、无 >4s 空洞，所以卡顿不是「取不到分片」，而是播放器侧行为。

1. **直播窗口只有 6s，而播放器被要求落后 15s。** 上游 `#EXTINF` 之和 ≈ 6.0s 可播放窗口，
   而目标偏移被固定为 `15s/8s/30s`，根本不可达——ExoPlayer 会长期按 0.97x 追赶够不到的偏移，
   位置持续漂移直到被滑动窗口甩到最老分片之外。日志痕迹：`pos=-2s dur=6s`（被夹到窗口起点）、
   `recovery kind=LIVE step=0 action=REFRESH_CURRENT reason=BUFFERING`。
   **修复**：`MediaEngine.setLiveWindowHintMs(windowMs)` 按实测窗口自适应。
   窗口 ≤12s 视为小窗口直播：目标偏移取窗口 40%、min 窗口/8、max 窗口×2/3，缓冲档
   `8s/16s/0.6s/1.5s`——**恢复水位必须小于窗口**，否则一次抖动就要等满整窗才出画
   （实测 6s 水位 + 6s 窗口 = 转圈 8s 后触发整会话重解析）。窗口未知或大窗口（公网 IPTV）
   保持 15s/8s/30s 不变。档位变化时释放播放器实例，下次 `prepare()` 以新参数重建。
2. **「僵尸源」把同线重试配额无限刷新。** 起播成功即清零 `sameLineRetries` 与「短暂 READY」叠加，
   配额永远用不完，App 死守一条「能出画面、几秒后必断」的死源，
   `engine rebuffer` 计数一路涨到 400+。
   **修复**：起播成功**不**立即清零，改由体检循环判定，**连续 60s 稳定出画**才恢复配额；
   僵尸源撑不到 60s，第 4 次失败即换线。
3. **取证**：`playback/PlaybackHealthLog.kt` 每 10s 采样、每 5 分钟打一行 `[HEALTH]`
   （引擎/状态/位置/缓冲/渲染帧数/丢帧/解码器初始化/中继/后端探活/解密池/恢复阶梯/内存/线程/网络）；
   卡顿时打多行 `PLAYBACK STALL DUMP`。**冻结判定**：`rendered` 帧数连续 30s 不增、
   而位置仍在前进（「时钟在走、画面不动」，既有两道看门狗只认 BUFFERING 超时与位置不前进，
   对这种形态不响）→ 打 `[STALL-DUMP]` 后交给**既有有限恢复阶梯**
   （刷新→换源→重建引擎→重置运行时；**不含整机自重启**，用户明确否决该项）。
   日志经 `OtvLog` 双写 logcat 与 `files/logs/otv.log`，重启 App 后仍能回看冻结前现场。

- **足球直播信号源行为**：起播快路径只解析首选源（1 次频道页 + 播放器页 + 解密）→ 立即起播；
  其余源 `streamUrlsIncremental` **到货即上屏**（不等最慢源，旧行为是 awaitAll 全源到齐才渲染选择条）；
  首选源 = 上次手动选择的信号源（`liveLastSrc` 持久化），记忆源不在本场动态线路表时回退 bb；
  手动切源即保存，自动故障换线不污染记忆。

### 3.5 卡密付费体系

- **码制**：`OTV-XXXXX-XXXXX`（10 有效字符，32 键字母表剔除 0/O/1/I）。套餐：monthly 30 天
  ¥9.9 / quarterly 90 天 ¥29.9 / yearly 365 天 ¥99.9 / lifetime 终身 ¥128（+weekly 周卡 7 天，
  非卖品）。**周卡改动需四层同步**：`LicenseManager.PLAN_DAYS`、`license_gen.py`、后台 UI、
  **PG `licenses_plan_check` 约束**，漏改则入库报 `DATABASE_23514`。
- **安全模型**：ECDSA P-256 + SHA256；**私钥只在本机**（`tools/keys/private_key.pem`），
  服务端只查表/计数/原样返回票据——服务端被黑也伪造不了授权。票据
  `{v,code,plan,days,issued,nonce,sig}`，canonical 串 `v|code|plan|days|issued|nonce` 本地验签。
- **协议 v2 与统一到期**：PostgreSQL 在首次激活时写入唯一 `activated_at` 和 `expire_at`；
  第二台设备只绑定，不重新计时。续费保留原卡为会员主卡，只延长统一 `expire_at`，
  新续费卡写入 `redeemed_at/redeemed_to` 后不可重复使用；公式仍为 `max(expire_at, now) + days`。
- **设备绑定**：服务端只认完整 64 位小写摘要。Android 为
  `SHA256(ANDROID_ID|packageName|Build.MODEL)`；Web 为 `SHA256(持久随机种子|origin)`；
  maxDev=2，同码同摘要幂等，`verify` 不会偷偷新增设备。
- **联网复验与 24 小时宽限**：App/Web 每 6 小时、启动/回前台/播放前复验。
  403/404/405/406 明确业务拒绝立即失效；断网、超时或 5xx 从最近一次成功复验起保留最多 24 小时，
  之后暂停播放，再次成功复验自动恢复。服务端 `serverNow/activatedAt/expireAt` 是时间权威，
  旧版最大时间戳账本和 HTTP Date 校时已移除。
- **门控**：全量门控（未激活禁看一切，路由层 `LicensePlayerGate` + 播放页二重校验）；
  DataStore `license.preferences_pb` 持久化。
- **Debug 包默认不门控**（`release` 固定 true、`debug` 固定 false，
  `-PdebugLicenseEnabled=true` 可在 Debug 上恢复真实卡密流程）——否则 UI 回归每跑一次
  就要消耗一个正式卡密槽位（一卡限 2 台设备）。契约测试
  `tools/tests/test_debug_license_gate_buildtype.py`。**Release 闸门未放宽。**
- 收款发货外包爱发电（主）/面包多（备）。

- **八个标签页**：总览 / 卡密 / 激活日志 / 补货 / 热更新 / 公告 / 电视源 / 影视源。卡密表展示
  首次激活、统一到期和续费去向；已消费续费卡只读，不再显示封禁或解绑操作。
- **热更新页**：「上传最新版本」按钮一键直传本地最新 zip（File System Access API 读本地目录，
  首次点击选 build_backend_zip.py 输出目录，目录句柄存 IndexedDB；需 Chrome/Edge 桌面版，
  且必须在普通桌面窗口里用——内嵌浏览器/后台窗口弹不出目录选择框，页面 12 秒后会提示改用
  「上传所选文件」）。首次要选的目录是 `android/app/src/main/assets/backend`
  （`internal/mobile/app/src/main/assets/backend` 是同一份镜像，选哪个都行）；
  无痕模式或「关闭时清除站点数据」下句柄不保留，页面会写明并提示改用本机脚本 `hu-upload.mjs`。
- **热更上传分片链路**：前端 >4.5MB 自动按 4MB/片 `POST /api/hu_upload_chunk?uid&seq`
  （暂存 `hu-uploads/{uid}/part-{seq}`，云函数多实例无粘性故状态外置；每片 3 次重试）→
  `POST /api/hu_upload_commit`（按序读回重组、尺寸精确校验、复用发布校验）→ 尽力清理暂存分片。
  ≤5MB 小包仍走直传 `/api/hu_upload`。**上限 96MB**，更大的包在本机签发后直传对象存储，或拆包。
- **补货**：后台「补货」页直接签发 + 入库（用户明确授权私钥上云）。env `OTV_PRIV_KEY` 存私钥 PEM
  （`license_gen.py` 的 `load_priv()` 优先读它）；产物写 `OTV_OUT_DIR`，入库走 env `OTV_AUTH_*`；
  `cards.csv` 以文本回传、页面给「下载 cards.csv」入口。
  **签名库不打在运行时里**：`cryptography` 由 `deploy/selfhosted/Dockerfile.admin` 在镜像构建时安装。
- **影视源管理**：草稿式新增 / 编辑 / 删除（保存只进草稿，「立即推送」才下发客户端）；
  「从网站新增」输入站点首页自动识别 MacCMS JSON/XML 接口，识别不到可手动填。列表带**测速**能力：
  每行可单独测速，「全部测速」并发 3 路探测所有源（macms 打 `?ac=list`、hhkan 打站内搜索页，
  接口 `POST /api/vod_source_speed`）；测完即自动按延时从快到慢排序，刷新后回到配置顺序；
  表头「延时」循环排序（配置顺序 → 由快到慢 → 由慢到快 → 配置顺序，▲/▼ 指示）；
  测速结果存 localStorage，刷新后保留。
- **电视源四步工作流**：**一切改动先入库草稿，点「发布并生效」才对客户端生效**
  （客户端 ≤30min 自动拉取）。
  ① 导入（M3U 文件 ≤32MB / 粘贴 / 上游 URL 仅 https 公网 ≤3 跳；合并=同名补线（推荐）/
  替换=清空重导（慎用））→ ② 编排（频道/线路/台标 CRUD + 批量启停 + 排序；台标上传 ≤2MB
  PNG/JPG/WEBP 存对象存储公开桶 `iptv/logos/`；客户端内置台标优先）→ ③ 发布（启用频道→m3u→
  对象存储公开桶 `iptv/iptv-latest.m3u` + 版本归档）→ ④ 回滚（复制归档对象回 latest 并
  **生成新版本号**，非拨指针）。
- **托管/自动双模式**：发布/回滚自动切托管（manual）并写 version.json；每日推流由定时器执行
  （7 段 cron `0 30 6 * * * *` = 每天 06:30），**不依赖本机、也不依赖后台页被打开**；
  托管模式下自动跳过、不覆盖手工列表。后台另有点「立即自动重建」手动跑一轮；
  「切自动模式」恢复每日推流（覆盖手动列表）。
- **「还原」按钮（2026-09-18）**：把该页维护的版本 / 记录清回初始状态。后端 `/api/reset_preview`
  （只读：返回将被清空的行数与确认短语）+ `/api/reset`（执行）。三条硬约束写在
  `tools/admin_server.py` 的 `RESET_SCOPES` 里：
  1. 必须同时提供**后台密码**与**逐页确认短语**（如「还原卡密」）——只有会话不足以授权销毁数据；
  2. 删除前把将删的行**完整导出**并随响应返回，前端自动下载 `admin-reset-*.json` 备份；
  3. 电视源只清版本历史与管理日志、**保留当前生效那一版**（`iptv_version` 保留 max(version)）；
     影视源两张表对服务账号是 403（只有 SECURITY DEFINER 函数能碰），该页按钮只做说明，
     要清空得在控制台跑 SQL。线上正在下发的 `iptv-latest.m3u`、`vod_source_versions` 永不触碰。

### 6.1 视觉系统与信息架构

**设计系统（中性专业暗色，2026-09-05 定稿）**：石墨底 `#0f1216/#151920/#1b2029` + 蓝单强调
`#4f8cff`（strong `#2f6be0` 专用于蓝底白字）+ hairline 分隔 + 等宽数字（Consolas + tabular-nums）；
正文 Segoe UI / 微软雅黑 13px；状态词汇封闭清单（`● 正常` / `● 已发布` / `○ 下线` /
`◌ 定时` / `✕ 封禁`…不得新造）；半径 6px 无阴影（浮层唯一投影）；
动效预算四处 ≤280ms + `prefers-reduced-motion` 全禁；中文短句动词开头；
禁 emoji / 主题化拟物 / 白底 / 第二强调色 / toast（底栏常驻条是唯一回执）。

**控制塔信息架构（2026-09-20/21）**：后台不是通用 SaaS 仪表盘，而是**控制塔**——状态先于装饰，
工作域清晰分区，当前任务处在中央，异常信号被单独抬高。

- 顶部状态带：产品标识、连接健康、班次/时间、全局会话状态。
- 左侧命令轨：按 Observe / Control / Publish / Sources 分组，当前工作域以亮色边缘和浅色底突出。
- 中央作业区：标题、关键指标、真实业务表格、当前操作表单；**表格列保持单行**。
- 右侧信号板：端点、存储、源站、下一次自动任务等需持续盯住的状态。
- 窄屏：命令轨变横向工作域条，信号板收进顶部抽屉，中央任务和表格仍可用。

配色语义：冷青 = 当前工作域与可操作焦点，绿 = 在线/完成，琥珀 = 待处理，
红 = 错误与破坏性风险；面板用不透明深色层，避免大面积玻璃和装饰渐变；圆角克制，
边界线比阴影重要；状态码/版本号/时间/哈希用等宽字体；桌面密度偏高但保持 8px 间距节奏。
动效只用于工作域切换、状态刷新和面板收拢，默认 <240ms。

**内容规则**：产品界面必须显示真实接口数据，不新增虚构指标、虚构用户或虚构发布状态；
设计稿的合成占位数据只能作结构占位，不能当产品指标；保留现有模块名、字段名和操作语义；
危险操作保持确认逻辑并在信号区显示结果，不用隐晦的纯颜色反馈。

**产品原则**：① 先让运维人员看见状态，再让他执行动作；② 高密度不等于拥挤；
③ 危险操作要有明确上下文、确认和结果回执；④ 数据表优先保持列对齐与单行可扫读，
窄屏用横向承载完整信息；⑤ 桌面效率优先，窄屏适配不牺牲业务可达性。
主要用户是产品负责人本人，典型工作区 1280–1600px 桌面宽屏。

## 7. 自建 VPS 基础设施

**线上主环境**：自建 VPS `103.236.97.137`。服务商做 NAT 端口映射，**不要改安全组与 NAT 映射**。

### 7.1 入口与端口

| 用途 | 外部 | 内部 |
|---|---|---|
| HTTPS 应用入口 | `35208` | 容器内 Nginx `8443` |
| 健康检查 | `25182` | 容器内 Nginx `8080`（只暴露 `/health`） |
| SSH | **`55560`**（NAT 映射到 22） | 22 |

- **SSH 外部端口是 55560**。用 22 会得到 `AuthenticationException`（**不是超时**），
  极易误判成「密码错误」。真端口以服务商控制台「产品详情」页为准，
  连接需 `look_for_keys=False, allow_agent=False`。
- VPS 仓库副本在 `/srv/mytv`，**不是 git 仓库**，部署靠同步目录后
  `docker compose -f deploy/selfhosted/compose.yaml up -d --build`。
- 密钥在 `/srv/mytv/secrets`（0600，不入库）。连接方式、端口映射与密钥布局见
  `deploy/selfhosted/README.md`；含密码的具体连接信息属机密，只存本机
  `.learnings/SERVER.md`（该目录已 gitignore）。

### 7.2 Nginx 路由（`deploy/selfhosted/nginx.conf`）

|---|---|

### 7.3 容器清单（`deploy/selfhosted/compose.yaml`）

常驻 10 个：`postgres` · `health` · `auth` · `storage` · `postgrest` · `business-api` ·
`web-api` · `admin` · `metadata-api` · `nginx`。
另有一次性/任务服务：`schema-migrations`（迁移，跑完退出）·
`apk-publisher` / `metadata-builder` / `metadata-refresh`（`ops` profile）。

### 7.4 `web-api` 容器环境

| 变量 | 值 | 说明 |
|---|---|---|
| `OTV_CLOUD_RELAY` | `0` | 整栈不依赖云端通用中继（迁移契约） |
| `OTV_VOD_LINE_INDEX_URL` | `http://storage:8092/v1/storages/object/hotupdate/vod-lines.json` | 本机解析好的静态片源索引（主兜底，无外部依赖） |
| `OTV_VOD_LINE_INDEX_MAX_AGE_DAYS` | `30` | 索引条目超过这个天数视为过期，不再使用 |
| `OTV_VOD_CLOUD_FALLBACK` | `0` | 旧的云端回源链路；自建栈已关闭 |
| `OTV_VOD_SOURCE_CONFIG_URL` | `http://business-api:8082/internal/vod-sources` | 后台发布的源配置（id 是数据库 UUID，与本机 slug 不同） |

片源兜底链在 `proxy.py::_vod_fallback_sources()` 里组装：配了索引就先用索引，
`OTV_VOD_CLOUD_FALLBACK=1` 才追加云端回源；两者都空则退回「暂无片源」。
以后给 VPS 找到能访问片源站的出口时，把 `OTV_VOD_LINE_INDEX_URL` 置空即可让服务器恢复实时匹配。

### 7.5 影视元数据中心

把「抓取 → 归一化 → 匹配 → 发布」从请求链路上挪下来，跑在同一台 VPS 上；设备端拿到的是
一份带版本号的 SQLite 包，`mytv_id` 从 10,000,001 起单调分配且跨版本稳定，
原 `douban:<id>` 引用继续有效。

```
/srv/mytv/metadata/snapshots/douban_snapshot.json   源快照（可由 VPS 自行刷新）
/srv/mytv/metadata/db/metadata-latest.sqlite        查询服务读取的当前库
/srv/mytv/objects/hotupdate/metadata/               公开产物：manifest.json、metadata-v<版本>.sqlite.gz、delta-*.sql.gz
```

- 版本号规则 `YYYYMMDDnn`（Asia/Shanghai）；内容没变时 `rebuild` 输出 `result=unchanged`，不产生新版本。
- 公开只读入口：`/metadata/health`、`/metadata/manifest.json`、`/metadata/search?q=`、`/metadata/<mytv_id>`。
- 服务版本 `metadata-api` 容器（内部 8094）；数据库只在容器网络内读取，不新开端口。
- 浏览器直连 `https://103.236.97.137:35208/metadata/...` 需要先信任迁移 CA；
  命令行用 `curl --cacert` 或 `-k` 验证。
- 抓取失败不影响发布：刷新脚本保留上一份快照继续重建，短期断源不会把线上影视搬空。

### 11.3 APK 版本号规则

用户于 2026-09-22 要求把 APK 版本与更新记录清零，版本号从 **V1.0** 重新开始、每版 **+0.1**：

| | 规则 | 例 |
|---|---|---|
| `versionName` | 界面展示用，`V主版本.次版本`，每版 +0.1 | V1.0 → V1.1 → V1.2 |
| `versionCode` | `主版本 × 100 + 次版本 × 10` | V1.0=100、V1.1=110、V1.2=120、V2.0=200 |

- `versionCode` 必须**严格递增**：客户端 `ApkUpdatePolicy.decide` 只比较它
  （`manifest.versionCode <= 本机` 即视为无更新），Android 系统也不允许低版本覆盖安装。
  V1.0 取 100 而非 10，就是为了高于重置前的 42，已装 1.4x 的设备仍能收到 V1.0 的更新提示。
- 默认值写在两个 `app/build.gradle`（`android/`、`internal/mobile/`），也可用 `-PapkVersionCode=` /
  `-PapkVersionName=` 临时覆盖。后台「版本发布 → APK 更新」页会按当前公开清单自动预填下一版的 +0.1 / +10。
- 次版本满 9 后进主版本（V1.9 → V2.0，code 190 → 200），避免与 `×100 + ×10` 编码冲突。

### 11.4 Release 入口门槛（硬 fail fast）

Release 必须显式传入**纯 origin**（结尾斜杠会被 normalize 去掉），端点由 `/activate`、
`/hotupdate` 等固定路径拼接：

```bash

# 方式二：统一环境变量

```

规则与报错文案在两套工程里**逐字节相同**，对称性由
`tools/tests/test_release_api_origin_contract.py` 断言，改动必须同步两处。

- **拒绝**：IP 字面量（除已 opt-in 的自建 VPS）、http、userinfo、query、fragment、任何路径。
- **迁移 CA + IP 入口默认只允许 Debug 本机联调**，正式包一律拒绝。
- **无正式域名时的显式双重 opt-in**：`-PallowIpReleaseOrigin=true`
  （或 `OTV_ALLOW_IP_RELEASE_ORIGIN=true`）**且** `apiBaseUrl` 恰好等于
  `https://103.236.97.137:35208`。此时才把 `src/ipRelease/res` 挂进 release 变体，
  由同名资源为**这一个 IP** 信任迁移 CA（`@raw/mytv_migration_ca`），其余域名仍只信任系统 CA；
  带路径的 IP 入口 opt-in 不豁免。
- 正式包的网络安全配置只信任系统 CA，迁移 CA 只留在 `src/debug/res/xml/network_security_config.xml`
  与 `src/ipRelease/res` 供本机联调。
- 内测版（neice flavor）：`./gradlew assembleNeiceRelease`（无卡密 / 热更门控）。
- 签名共用 `optimaltv-release.keystore`（10 年）；不混淆（Chaquopy + 反射保守）。

### 11.5 Windows EXE 构建与运行

Windows 版是单文件便携 EXE：`pywebview` 使用系统 WebView2 打开本机
`proxy.py` 托管的 `www/`，不跳转到云端网页版。后端 Python 模块、豆瓣与
hhkan 快照、内容寻址的网页资源、固定版本的 hls.js@1.5.13 均收进 EXE。
Windows QuickJS 由 `quickjs` 的本机 `.pyd` 提供，目标电脑无需安装 Python 或 Node；
需有 Microsoft Edge WebView2 Runtime。卡密门控仍按网页版规则执行。

```powershell
python -m pip install -r desktop/requirements-build.txt
python desktop/build.py                       # apk/Windows版/MyTV.exe
$exe = (Resolve-Path 'apk/Windows版/MyTV.exe').Path
$p = Start-Process -FilePath $exe -ArgumentList '--self-test' -Wait -PassThru -WindowStyle Hidden

```

`desktop/build.py` 只读 `tools/backend-src/`，复用 Android 后端文件清单，但不调用
会改动 APK assets 的 `build_backend_zip.py main()`。构建时校验 HLS 脚本的固定
SHA-256；首次需联网下载，随后可加 `--offline` 使用本地缓存。
`apk/Windows版/` 已被 Git 忽略，EXE 不入库。

首次运行把 `backend.zip` 按 SHA-256 安全解压到
`%LOCALAPPDATA%\MyTV\backend\<sha>`；数据库、图片缓存、WebView2 用户数据和日志
分别保存在 `%LOCALAPPDATA%\MyTV\data`、`webview-profile`、`logs` 等目录。
本机服务只绑定 `127.0.0.1`，优先用 8090；被占用时按 8091 起的固定顺序
寻找空闲端口（最多 64 个），避免每次启动随机换 origin。
云端激活、IPTV 与元数据端点默认指向当前自建 VPS 的 HTTPS 入口，沿用仓库内的
迁移 CA 公钥并保持证书校验；可用 `OTV_DESKTOP_API_BASE_URL` 指定另一个纯 HTTPS origin。

**自动更新（2026-09-30 新增）**：桌面版复用服务端既有的 `/hotupdate/check`
契约与热更 zip，不需要第二套发布流程——服务端照旧用 `hu-upload.mjs` 发包。
`desktop/updater.py` 在窗口起来后开一条守护线程静默检查、下载、校验并暂存，
**下次启动生效**，不打断正在播放的用户。「我的」页右上有版本号与「检查更新」

更新范围 = `backend.zip` 里的全部内容（后端模块 + `www` 前端 + 快照）。
**EXE 壳本身不在范围内**——PyInstaller 冻结的 launcher/webview/quickjs
改动仍需重新构建分发。失败策略是静默回退内置包：网络、校验、解压任一环节
出错都退回内置 `backend.zip` 并照常启动，更新永远不能把应用卡死。
安全口径与内置包解压一致：拒绝绝对路径、`..`、盘符冒号与符号链接；

改变浏览器 origin，原端口下的卡密票据与 localStorage 不会自动迁移；应先关闭
占用 8090 的程序并重启 EXE，回到原端口恢复原有浏览器存储。
网页所用外部图片与直播源仍受目标电脑网络可达性影响。

**2026-09-30 自动更新实测**：更新器 17 项专项测试通过（桌面端共 67 项、
后端 584 项、网页契约 412 项）。真实 HTTP socket 上跑通
检查→下载→SHA-256 校验→安全解压→下次启动选用新包；三种降级场景

**2026-09-30 线上联调修正（三个真实缺陷）**：上条 502 的判断后来被证伪，
实际原因是**本机系统代理**（Clash `127.0.0.1:4210`）拦截了到裸 IP 的请求。
VPS 侧实测：10 个容器全部 Up，nginx 内部各上游均 200，
`127.0.0.1:8443`（nginx 直连）200，而 `35208` 在 VPS 本机无监听——

1. **系统代理**：`urllib` 默认跟随 Windows 系统代理，热更/卡密会被本地代理
   拦掉。改为 `direct_opener()` 显式 `ProxyHandler({})` 绕过，但仍传入
   launcher 装载的迁移 CA context——绕过代理不以牺牲证书校验为代价。
2. **deviceId 形状**：原先硬编码 `"desktop"`，被服务端
   `api_service.py` 的 `re.fullmatch(r"[a-f0-9]{64}", device_id)` 判
   `bad_device`。改为本地持久化的 64 位十六进制 id
   （`%LOCALAPPDATA%\MyTV\device-id`），与网页端 `webDeviceId()` 同形状。
3. **包大小字段**：服务端下发的是 `fileSize`，原先只读 `size`，
   导致大小校验被静默跳过。同时补上 `hotVersionCode` 版本号回落。

#### 13.4.3 遗留缺陷详情

**BUG-01 · JWT 篡改检测 flaky（✅ 已修复）** — 现象：30 次跑挂 5 次（16.7%）。
根因（20000 次采样实测）：HMAC-SHA256 的 32 字节编码成 43 字符 base64url，
**低 2 bit 是填充位、解码时丢弃**，同 4 字符组内的末位字符（`A`/`B`/`C`/`D`）
解码出**完全相同的签名字节**。原测试固定把末位改成 `'A'/'B'`，当原末位落在该组时
等于什么都没改。理论 no-op 率 4/64 = 6.25%，实测 1198/20000 = 5.99%。
**产品校验是对的**：字节不同的 18802 次篡改全部被正确拒绝。修复：改为翻转真实签名字节
（`raw[10] ^= 0xFF`）再回编。复验 40/40 通过。

**BUG-02 · hhkan 简介/标题显示 HTML 实体字面量（P2，✅ 已修复，真机已验证）**

现象：移动端首页/收藏/历史/播放器的简介与标题直接显示 `&#039;`/`&quot;` 字面量，
19/49 份 UI dump 命中。

**根因是两条路径都漏了解码，不是一条：**

1. **实时抓取（常态路径）**：`proxy.py` 的 `/hhkan/detail` 是「先实时抓取，失败才回落快照」：

       d = hhkan.parse_detail(_hhkan_origin_call(lambda: hhkan.get_page(...)), vid)
       except Exception: d = _HHKAN_SNAPSHOT.detail(vid) or {}

    而 `hhkan.parse_detail` 里 `title` 直接取 `re.search` 原文、`desc` 只做
    「去标签 + 替换 `<br>`」，**从未调用含 `html.unescape` 的 `_clean_text`**
    （`_clean_text` 只用在卡片解析 `_parse_card` / `_parse_list`）。
2. **快照容灾路径**：`hhkan_snapshot.py` 的 `load_default()/detail()` 直接 `json.loads`
    原始字符串，也不解码。随包快照里确实有 72 处实体（desc 18 / ep 9 / title 1）。

**只修快照是不够的**——首轮我只改了 `hhkan_snapshot.py`，单测全绿、实机复测接口
**仍返回 2 个 `&#039;`**，才发现常态路径走的是实时抓取。这是本次的教训：
子代理报的「客户端缺解码」被我复核成「后端快照脏」，但我只验到一半就收工了。

**修复**（服务端，不改客户端——脏数据在服务端，客户端解码等于「猜着还原」）：

- `hhkan_snapshot.py`：新增 `_decode_entities()` / `_decode_tree()`，在
  `SnapshotCatalog.__init__` 里统一解码一次。放在构造期而非各读取方法，
  是为了「读出的文本不含实体」这条不变式对所有入口（含直接 `SnapshotCatalog(raw)`）都成立。
- `hhkan.py`：新增 `_decode_text()`（只解码不剥标签，给已 `re.search` 出的纯文本片段），
  `parse_detail` 的 `title` / `desc` 走它。`desc` 里 `<br>` 的还原必须在
  `unescape` **之前**做——源站写的是 `&lt;br&gt;`。

**关于解码层数**：原先假定「只解一层」，实机复测发现随包快照里存在**双重转义**
（`details.378068.desc` 磁盘上是 `&amp;quot;Bridal Shower&amp;quot;`），只解一层会把
`&quot;` 字面量留给用户。改为**解到收敛为止**（`_MAX_DECODE_PASSES = 5` 作防御，
`decoded == value` 提前退出）。裸 `&`（`AT&T`）不含分号实体，不受影响。

**真机验证**（内置模拟器 `MyTV_Mobile_API30`）：同一接口 `/hhkan/detail/375951`

## 15. 已知限制与风险

### 15.1 片源与出口限制（当前最大的未闭环项）

- **网页版片源覆盖取决于索引新旧**：VPS 出网访问 macCMS 系片源站（`www.hongniuzy2.com`、
  `www.haohankan.com`、`bfzyapi.com` 等）IPv4/IPv6 全部连接超时，服务器侧实时匹配必为空。
  主兜底是 §14.2 的本机静态索引。代价是：① 新片 / 冷门片要等下一次重建索引才有线路；
  ② 索引默认 30 天过期。**App 端不受影响**——设备取源在**本机网络**实时完成
  （`EmbeddedBackend` 起 `proxy.py`，`baseUrl=127.0.0.1`）。
- **VPS 也够不着部分视频 CDN**：片源分片（如 `hnts.ymuuy.com:65`、`c.baisiweiting.com:18443`）
  在 VPS 上超时，中继会 499。网页播放已改为「浏览器直连优先、失败回中继」绕开；
  但**纯 http 直链仍只能走中继**，这类片源在网页版会失败（App 端不受影响）。
- **「N 条合格线路」≠「N 部可播」**：那是 API 匹配评分的结果。猫眼媒体主机从 VPS 拉流本身不稳定
  （三次里两次 20~25s 超时），所以服务器代拉这条路受上游限制。平板 / 手机 App 走设备自己的网络，
  不受这个影响——平板能正常看与「VPS 出口访问第三方片源 API 失败」并不矛盾：
  后者说的是 VPS 出口，不是 App 不可用。
- 直播、搜索、目录、元数据接口不受上述问题影响，已在 VPS 上实测通过
  （直播源多在国内 IPTV 主机，VPS 可达）。
- **网页版播放尚未完成浏览器出画验收**：点播放会弹会员激活，网页的换线选择逻辑目前只有
  Node harness 层面的验证，没有真实浏览器出画证据。

### 15.4 国家队队标缺失（BUG-04，2026-09-29 已修）

**现象**：足球页国家队队标大面积缺失，客户端只显示首字兜底。

**排查中纠正过的两次误判**（先记下来，免得下次重走）：

1. 「48 个国家队全部缺失」——**错**。判定有 4 层（`KNOWN_MAP` 静态表 466 条 →
   磁盘缓存 → football-logos.cc → TheSportsDB），`team_icon_cache.json` 里 266/323
   条 `url=None` 看着很惨，但 `KNOWN_MAP` 静态表兜住了 42 个。缓存空 ≠ 队标缺失。
2. 「6 个英格兰队没有队标」——**错**。它们有 `fd_id`，只是 `crests.football-data.org`
   抓取间歇性失败。

**真根因**：`proxy.py::fetch_svg_icon` 的抓取在**并发**下不可靠。

    修复前（模拟器实测，48 个国家队同时请求）：
      第 1 轮 6/16 失败（38%），返回 68 字节的 1x1 透明占位图
      串行执行则 0 失败

三个叠加缺陷：

1. `urlopen(timeout=6)` 只试一次，**无重试**；
2. **对上游无并发上限**——48 个同时打，设备侧带宽被打满；
3. 失败**既不落盘也不记失败缓存**，下个请求照打，上游继续限流。

放大问题的是 `timeout=6` 太紧：同一个 SVG **本机 0.9s、设备（移动网络到境外
CDN）要 5~6s**，而利物浦的 SVG 有 299KB。三个因素叠加，用户就看到「队标大面积缺失」。

**修复**（`proxy.py`，三处）：

| 改动 | 作用 |
|---|---|
| `SVG_ICON_FETCH_SEMAPHORE = Semaphore(4)` | 对上游限流，同一时刻最多 4 个请求，其余排队 |
| `SVG_ICON_FETCH_ATTEMPTS = 3` + 退避 | 单次失败自动重试 |
| `SVG_ICON_FETCH_TIMEOUT = 20`（原写死 6） | 慢网下也能等到大文件 |
| 每 URL 一把 `_svg_fetch_lock` | 同一队标的并发请求只打一次上游，其余复用结果 |

锁内做了 double-check（等锁期间前一个线程可能已写好缓存），避免重复打上游。

**真机验证**（内置模拟器 `MyTV_Mobile_API30`，清空热更 + SVG 缓存 = 冷启动）：

    修复前：48 队并发 → 8 个失败
    加重试+放宽超时后：3 个失败（都是大文件）
    加并发闸门后：第 1 轮 0 个失败（29.5s）、第 2 轮 0 个失败（4.3s，缓存命中）

29.5s 是 48 个全量的总耗时，**不阻塞首屏**：队标走 `/api/team-icon-img` 按需加载，
用户滚到哪个才请求哪个，单个不受影响（真机绝大多数 1~2s 就回）。

测试 543 → 553（后端全量 OK），新增 `tests/test_team_icon_fetch_resilience.py` 10 项：
重试后成功 / 成功后落盘 / 磁盘缓存不重复打上游 / 全失败如实返回 / 同 URL 并发只打一次
/ 超时值够大且真的被使用 / 重试预算 / 存在并发闸门且 <=8 / N 个不同 URL 并发不超闸门。

**另一个坑**：`tools/backend-src/svg_icon_cache/`（35 个）与 `transparent_icon_cache/`
（130 个）**是入库的**——队标随包分发，首装无网时也能显示。不要以为它们是运行期缓存
就 `git checkout` / `git clean` 掉，那会删掉 165 个队标文件。

### 15.6 影视源「撤销 / 回滚」（BUG-06，2026-09-29 已加）

**问题**：`admin.html` 的影视源 tab 只有「删除」，而 `vod_source_admin_delete` 直接
`delete from vod_source_drafts where id=p_id`——**不可逆**。误删一个源后只能靠 SQL
手工补回；想整体回退又会把其它源期间做的改动一并丢掉。

**基础已经有了**：`vod_source_versions` 存着每次发布的**完整配置快照**
（`config` jsonb，含 sources 全字段与当时的 `revision`）。所以撤销 = 把 drafts
按某个历史版本重建，而不是去动历史。

**新增两个 RPC**（`tools/vod_source_undo_migration.sql`）：

- `vod_source_admin_versions()` — 列出可回滚版本（新到旧）：版本号 / 时间 / 源数量 / sha256
- `vod_source_admin_rollback(p_version)` — 把 drafts 按该版本快照重建

两条设计约束写进了 SQL 注释，任何调用方都绕不过：

1. **历史版本是只追加账本**：回滚只改 drafts，函数里**没有**
   `delete from vod_source_versions` / `truncate`——否则「撤销」本身也变得不可撤销。
2. **回滚不隐式发布**：改完 drafts 仍需显式点「立即推送」才对线上生效。
   否则用户会以为「撤销了」而线上其实还是那份配置。契约测试专门锁了这条
   （`test_rollback_endpoint_does_not_publish_implicitly`）。

锁与 `publish` 用同一张 `versions` 表做锚（`for update` + `lock table`），
避免回滚与发布交叉。`sort_order` 取快照里的数组下标，保持与当时发布一致的顺序。

**后台入口**：影视源 tab 顶部「历史 / 撤销」按钮，弹窗列出各版本

### 15.8 影视源清理 + 设备侧测速（2026-09-30）

#### 为什么后台的「测速」不能用来判断源死没死

后台测速跑在 **VPS** 上，而 App 的内嵌后端跑在**用户手机**上——两条完全不同的
网络出口。2026-09-30 实测（10 个源）：

| 判定路径 | 结果 |
|---|---|
| 后台测速（VPS） | 猫眼 430ms、VN影视 779ms，**其余 8 个「失败」** |
| 实机取线路（设备网络） | 10 个源**全部**能取到线路 |
| 实机取流（直链 200） | 7 个 OK，只有虎牙的 CDN SSL 挂、暴风该集 404 |

原因：磐石云无境外出口，8 个源挂在 Cloudflare 段（104.21.x / 172.67.x），
从 VPS 必然超时（`docs` §7.4 已记）。**照后台结果清理会砍掉 App 里能用的线路。**

#### 新增：设备侧探活通道

`vod_sources.py` 新增 `probe_source()` / `probe_all_sources()`，内嵌后端暴露
`/vod/sources/probe`，后台新增「设备侧测速」按钮（`/api/vod_source_probe_device`
转发到 App 报上来的内嵌后端地址，**不在 VPS 上自己 ping**）。

设计约束：

- 走 macms 最轻的 `?ac=list`，不为探活拉整页数据；
- `PROBE_CONCURRENCY = 4` 上限——源站普遍限流，20 个源同时打会把好源也挤失败；
- `PROBE_TIMEOUT = 8.0` 独立超时，一个卡住的源不拖垮整批；
- 错误摘要剥掉 URL query 并截断到 120 字（上游报错可能带签名 token）；
- Cloudflare 挑战页识别为 `challenge page`，不误报 ok。

**实机验证**：10 个源 3.6~9.8s 测完，全部可用（猫眼偶发 SSL 抖动，5 次里 4 次通，
属源站限流而非失效——探活如实反映了这点）。

#### 本轮清理与补充

## 16. 合规与安全边界

### 16.1 影视源合规边界

当前配置的影视源均属于无授权聚合 / 采集类站点，项目没有取得其内容授权。
技术上的多源兜底、测速和中继只解决可用性，不构成法律豁免。

- 影视源可用性由测速和失败降权机制维护；来源或域名变化时重新评估。
- 个人 / 家庭自用的传播风险相对较低但不为零；公开分发、持续收费或对无授权内容收费会显著放大风险。
- 如转为公开产品，应替换为已授权内容源，并重新评估卡密收费与公网访问面。
- 第三方队标、海报和素材应记录来源与授权边界，不能因「非商用」自动推断为无限制使用。

### 16.2 安全边界

- 私钥、卡密 CSV、服务密钥、Cookie 和长期令牌不得进入 Git、云端部署包或文档。
- 播放源和第三方素材必须记录来源与授权边界；非商业素材不能默认推断为可商业使用。
- 变更公网接口、RLS、后台权限或热更新校验时，必须增加对应契约测试并记录回滚方式。

### 17.2 量化基线（2026-09-29 实测，方案 §1.2）

方案 §1.2 的指标表此前一直空着，注明"上线前必须先采集现网基线"。以下为首次
采集结果，**样本量小、且是在模拟器 + swiftshader 软渲染下测得**，只能作为
后续对比的起点，不能当作"达标/未达标"的结论。

采集方式：App 内置 `PlaybackTelemetry`（logcat tag `OTV-TELEMETRY`）按单调时钟
记录各阶段耗时；解析脚本 `artifacts/perf-baseline-from-logcat.py`，原始数据
`artifacts/perf-baseline-tv.json`。

样本：TV 版 v1.3（versionCode 130），`emulator-5554`，影片《肖申克的救赎》，
冷启动后首次播放，从点播放到出画。

| 指标 | 方案目标 | 实测 | 说明 |
|---|---:|---:|---|
| 首条片源返回 | P50 ≤ 500ms | **129ms** | `tier=local_detail`，命中本地详情缓存，未走网络匹配 |
| 点播放到首帧 | P50 ≤ 2.0s / P95 ≤ 4.0s | **78.8s** | 严重超标，见下方拆解 |
| 自动换线次数 | — | **18 次** | line 0 → 12 |
| 引擎回退（→VLC） | — | 0 | 全程 Media3 |
| 播放失败（fatal） | — | 0 | 最终出画 |

**78.8 秒是怎么来的**：前 11 条线路每条都精确等待约 5.0s 首帧看门狗才换线
（埋点 `first frame 5012ms → line 1` … `5049ms → line 4`），第 12 条线路
在 78.8s 出画。也就是说这条片子的线路排序把不可用线路排在前面，每次换线
都要赔 5 秒。

结论与后续：

- 片源解析（§6 匹配链）本身达标，129ms 命中本地缓存；
- 瓶颈在**线路可用性排序**而非解析速度——静态索引里的线路顺序没有反映
  实际可用性，导致逐条试错。这属于方案 §7「片源健康评分」未真正生效：
  代码里有 `match_score` 与后台测速，但 App 侧起播时用的是未经健康度加权的
  原始顺序；
- 首帧看门狗 5s 这个固定值在"前几条都不可用"时会线性放大总时长，
  §1.2 要求的"自动换线恢复 1～3s"在此场景下不成立；
- 需要补的实测：移动端样本、长播 30 分钟重缓冲率、UI 帧率、片库首屏。
  这些本机模拟器软渲染条件下测不出可信数据，建议在真机上补。

采集工具：

```powershell

python artifacts/collect-perf-baseline.py --serial emulator-5554 `
    --package com.qiubo.optimaltv.public
# 离线补算（已有 logcat 文本时）

```

### 17.4 结论

方案的**功能类要求基本落地**：片源匹配链、健康评分、快速起播、播放器回退、
熔断换线、CloudBase 运行时下线、服务端与客户端验收清单均有代码与实测支撑。

尚未达成的是三类：**量化基线只采了 TV 端一组**（§17.2，其余指标仍空）、
**正式域名与公共证书未启用**（§13.2，用户已确认用 IP 方案）、**部分架构建议
未采纳**（独立 Resolver 服务、三张表、Redis、灰度），这些都有等价或更轻量的
替代实现。

§17.2 的实测还暴露一个此前没被记录的问题：片源解析达标（129ms），但线路
排序未按健康度加权，导致起播时逐条试错、78.8s 才出画。这是下一轮优化的
第一优先项。
