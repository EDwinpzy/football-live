## 1. 产品概览

**My TV（OptimalTV 工程）**：Android 原生影视应用（TV 大屏 + 手机/平板双端）+ 云端网页版，
Kotlin + Jetpack Compose + Media3，tvOS 深色风格。影片卡片、详情和筛选以豆瓣目录为准，
播放线路来自后台可管理的现有影视源。**后端打包进 app**（Chaquopy 内嵌 Python），
每台设备直接访问公网内容源与播放源。商业化 = 卡密付费（公测版门控）。

### 发布边界

- 本机是唯一代码整理、构建和 Git 发布入口。
- 后端与 `www/` 使用同一份内容寻址 zip，在后台静默下载、SHA-256 + 结构校验后只重启
  `:backend` 进程，App 前端不弹窗。
- Kotlin / Compose 等原生 UI 无法由 Python zip 替换，必须构建签名 APK 交给 Android 系统安装器更新。
- 足球队标使用「内置映射优先 → football-logos.cc 在线补全 → 磁盘缓存 → TheSportsDB → 文字兜底」。
  按非商业粉丝项目使用该站资源，不把全量队标打包进 APK；后端保存已解析结果，站点不可用时仍保留回退链。

### 产品矩阵（单 variant，2 APK + 1 网页）

### 核心能力一览

影视点播（首页/全部/详情选集/搜索/收藏/历史）· 卫视直播（精编频道表 + 多源备份无感切换）·

## 3. 端侧功能模块

### 3.1 影视点播与搜索

- 目录/卡片/元数据以**豆瓣目录**为准（`douban_catalog.py`），搜索支持拼音输入法
  （AOSP 谷歌拼音解码器 `cpp/pinyinime`）与首字母联想（构建期两张 asset 表：
  `tools/gen_pinyin_initials.py` / `gen_pinyin_titles.py`）。
- **hhkan 容灾**：本地与 Android 优先实时抓取；源站风控时读取构建期
  `hhkan_snapshot.json`（固定三栏目、搜索、筛选、分页与详情均不切换目录来源）。
  5 分钟熔断器保证同实例只做一次失败探测，到期半开恢复；快照不访问 PG。
- **macCMS 播放补充池**：暴风、极速、金鹰、虎牙、豪华、红牛、速播、360 等 T1 源，
  仅在详情之后按同名影片追加播放线路；不得生成卡片、替换目录或改变分类。
  站级并行测速排序（5min）+ 故障自动换站；线路级清晰度排序（实读 RESOLUTION，死线沉底）；
  pid≥100 使用站点命名空间，≥720p 线路优先供播放器自动选择。补线总开关 env `OTV_ENRICH=0` 可关闭。
- **片库筛选三态判定**：上游空壳响应不得当成空结果（降级链 + 冷却），上游不可用时走
  快照实测汇总 + 本地保守判定。分类 × 参数能力矩阵数据化
  （`tools/backend-src/douban_filter_matrix.json`，探测脚本 `tools/probe_douban_filter_matrix.py`），
  准确度自检 `tools/check_vod_filter_accuracy.py`。
  **无实测数据时一律本地判定——宁可少给，不给错。**
- **片库 LazyColumn 的 item key 必须用板块名**（`lib-sec-{sec.name}-r{ri}`）：
  三块到货顺序与 blockOrder 展示顺序不一致，序号 key 会让迟到板块插入触发全部行 item 重建
  → 聚焦节点销毁、焦点乱甩（TV 端「光标跳行」的根因）。TV 与移动版同款布局同规则。

### 3.2 卫视直播与 IPTV

- 卫视直播：精编频道表内置（assets `iptv_curated.m3u`），台标本地图标（`tools/build_logo_assets.py`
  生成，序号=已落盘最大+1 防串台；暗标白化 normalize_logo），自动补源、多源备份无感切换。
- IPTV 电视：SOURCES = 云端桶 latest（首位）+ Guovin（gh-proxy/jsdelivr）+ vbskycn；
  快照落 `files/iptv_snapshot.m3u` 先读秒上屏；刷新节流 ≤30min。
- 测速换台：`rankUrls()` TTFB 测速排序起播即最快线；BUFFERING>3.5s 且备线分值
  <0.55×当前 → 无感切换；侧边栏 60s 周期探测组内前 40 线路。
- 播放健壮性：首帧看门狗（READY 15s 无首帧→切 VLC）；fatalMsg 12s 未恢复自动跳台
  （环形，连续 3 次上限）；ac3/eac3/dts 音轨自动转 VLC。
- **SSRF 双层校验** `data/source/UrlGuard.kt`：仅 http/https、拒私网/环回/IPv4-mapped，
  `assertPublicResolved()` DNS 全 A 记录私网则拒；列表拉取侧 + 起播侧两层。

### 3.3 播放引擎

- 三级回退：Media3 硬解 → 中继 HLS → libVLC；点播直播共用会话代数管理（engineEpoch）。
- 直播 HLS 经本机中继（签名 ~9 分钟轮换 + 90s 续签热切换）；解密中继 `StreamDecryptServer`
  用 **3-WebView 解密池**（信号量 + 槽位并发，串行→3.2× 吞吐，替代单实例全局锁）。
- 足球解密三级分发：端内 QuickJS HTTP bridge（:8091）/ 本地 node / 云函数 `decrypt_python.py`。
- **解密池自愈**：`StreamDecryptServer` 的 WebView 加 `WebViewClient.onRenderProcessGone`
  → 销毁清槽懒重建；12s 零回调僵死检测兜底（渲染进程活着但页面级僵死的形态）；
  poll/loadData 全面 runCatching。根治「反复加载混淆页数小时后渲染进程崩溃 → 僵死 WebView 永久
  留池 → 每次解密 12s 超时 → 三槽全僵 =『半小时后所有信号源失效』」。

#### 直播长跑稳定性（2026-09-16）— 三个根因与对应修复

用户报「播十几二十分钟后画面冻住，退出重进才好」。供给侧实测是健康的：中继日志逐条统计分片请求，
序号无跳号、无 >4s 空洞，所以卡顿不是「取不到分片」，而是播放器侧行为。

1. **直播窗口只有 6s，而播放器被要求落后 15s。** 上游 `#EXTINF` 之和 ≈ 6.0s 可播放窗口，
   而目标偏移被固定为 `15s/8s/30s`，根本不可达——ExoPlayer 会长期按 0.97x 追赶够不到的偏移，
   位置持续漂移直到被滑动窗口甩到最老分片之外。日志痕迹：`pos=-2s dur=6s`（被夹到窗口起点）、
   `recovery kind=LIVE step=0 action=REFRESH_CURRENT reason=BUFFERING`。
   **修复**：`MediaEngine.setLiveWindowHintMs(windowMs)` 按实测窗口自适应。
   窗口 ≤12s 视为小窗口直播：目标偏移取窗口 40%、min 窗口/8、max 窗口×2/3，缓冲档
   `8s/16s/0.6s/1.5s`——**恢复水位必须小于窗口**，否则一次抖动就要等满整窗才出画
   （实测 6s 水位 + 6s 窗口 = 转圈 8s 后触发整会话重解析）。窗口未知或大窗口（公网 IPTV）
   保持 15s/8s/30s 不变。档位变化时释放播放器实例，下次 `prepare()` 以新参数重建。
2. **「僵尸源」把同线重试配额无限刷新。** 起播成功即清零 `sameLineRetries` 与「短暂 READY」叠加，
   配额永远用不完，App 死守一条「能出画面、几秒后必断」的死源，
   `engine rebuffer` 计数一路涨到 400+。
   **修复**：起播成功**不**立即清零，改由体检循环判定，**连续 60s 稳定出画**才恢复配额；
   僵尸源撑不到 60s，第 4 次失败即换线。
3. **取证**：`playback/PlaybackHealthLog.kt` 每 10s 采样、每 5 分钟打一行 `[HEALTH]`
   （引擎/状态/位置/缓冲/渲染帧数/丢帧/解码器初始化/中继/后端探活/解密池/恢复阶梯/内存/线程/网络）；
   卡顿时打多行 `PLAYBACK STALL DUMP`。**冻结判定**：`rendered` 帧数连续 30s 不增、
   而位置仍在前进（「时钟在走、画面不动」，既有两道看门狗只认 BUFFERING 超时与位置不前进，
   对这种形态不响）→ 打 `[STALL-DUMP]` 后交给**既有有限恢复阶梯**
   （刷新→换源→重建引擎→重置运行时；**不含整机自重启**，用户明确否决该项）。
   日志经 `OtvLog` 双写 logcat 与 `files/logs/otv.log`，重启 App 后仍能回看冻结前现场。

- **足球直播信号源行为**：起播快路径只解析首选源（1 次频道页 + 播放器页 + 解密）→ 立即起播；
  其余源 `streamUrlsIncremental` **到货即上屏**（不等最慢源，旧行为是 awaitAll 全源到齐才渲染选择条）；
  首选源 = 上次手动选择的信号源（`liveLastSrc` 持久化），记忆源不在本场动态线路表时回退 bb；
  手动切源即保存，自动故障换线不污染记忆。

### 3.5 卡密付费体系

- **码制**：`OTV-XXXXX-XXXXX`（10 有效字符，32 键字母表剔除 0/O/1/I）。套餐：monthly 30 天
  ¥9.9 / quarterly 90 天 ¥29.9 / yearly 365 天 ¥99.9 / lifetime 终身 ¥128（+weekly 周卡 7 天，
  非卖品）。**周卡改动需四层同步**：`LicenseManager.PLAN_DAYS`、`license_gen.py`、后台 UI、
  **PG `licenses_plan_check` 约束**，漏改则入库报 `DATABASE_23514`。
- **安全模型**：ECDSA P-256 + SHA256；**私钥只在本机**（`tools/keys/private_key.pem`），
  服务端只查表/计数/原样返回票据——服务端被黑也伪造不了授权。票据
  `{v,code,plan,days,issued,nonce,sig}`，canonical 串 `v|code|plan|days|issued|nonce` 本地验签。
- **协议 v2 与统一到期**：PostgreSQL 在首次激活时写入唯一 `activated_at` 和 `expire_at`；
  第二台设备只绑定，不重新计时。续费保留原卡为会员主卡，只延长统一 `expire_at`，
  新续费卡写入 `redeemed_at/redeemed_to` 后不可重复使用；公式仍为 `max(expire_at, now) + days`。
- **设备绑定**：服务端只认完整 64 位小写摘要。Android 为
  `SHA256(ANDROID_ID|packageName|Build.MODEL)`；Web 为 `SHA256(持久随机种子|origin)`；
  maxDev=2，同码同摘要幂等，`verify` 不会偷偷新增设备。
- **联网复验与 24 小时宽限**：App/Web 每 6 小时、启动/回前台/播放前复验。
  403/404/405/406 明确业务拒绝立即失效；断网、超时或 5xx 从最近一次成功复验起保留最多 24 小时，
  之后暂停播放，再次成功复验自动恢复。服务端 `serverNow/activatedAt/expireAt` 是时间权威，
  旧版最大时间戳账本和 HTTP Date 校时已移除。
- **门控**：全量门控（未激活禁看一切，路由层 `LicensePlayerGate` + 播放页二重校验）；
  DataStore `license.preferences_pb` 持久化。
- **Debug 包默认不门控**（`release` 固定 true、`debug` 固定 false，
  `-PdebugLicenseEnabled=true` 可在 Debug 上恢复真实卡密流程）——否则 UI 回归每跑一次

### 7.4 `web-api` 容器环境

| 变量 | 值 | 说明 |
|---|---|---|
| `OTV_CLOUD_RELAY` | `0` | 整栈不依赖云端通用中继（迁移契约） |
| `OTV_VOD_LINE_INDEX_URL` | `http://storage:8092/v1/storages/object/hotupdate/vod-lines.json` | 本机解析好的静态片源索引（主兜底，无外部依赖） |
| `OTV_VOD_LINE_INDEX_MAX_AGE_DAYS` | `30` | 索引条目超过这个天数视为过期，不再使用 |
| `OTV_VOD_CLOUD_FALLBACK` | `0` | 旧的云端回源链路；自建栈已关闭 |
| `OTV_VOD_SOURCE_CONFIG_URL` | `http://business-api:8082/internal/vod-sources` | 后台发布的源配置（id 是数据库 UUID，与本机 slug 不同） |

`OTV_VOD_CLOUD_FALLBACK=1` 才追加云端回源；两者都空则退回「暂无片源」。
以后给 VPS 找到能访问片源站的出口时，把 `OTV_VOD_LINE_INDEX_URL` 置空即可让服务器恢复实时匹配。

### 7.5 影视元数据中心

把「抓取 → 归一化 → 匹配 → 发布」从请求链路上挪下来，跑在同一台 VPS 上；设备端拿到的是
一份带版本号的 SQLite 包，`mytv_id` 从 10,000,001 起单调分配且跨版本稳定，
原 `douban:<id>` 引用继续有效。

```

/srv/mytv/metadata/db/metadata-latest.sqlite        查询服务读取的当前库
/srv/mytv/objects/hotupdate/metadata/               公开产物：manifest.json、metadata-v<版本>.sqlite.gz、delta-*.sql.gz
```

- 版本号规则 `YYYYMMDDnn`（Asia/Shanghai）；内容没变时 `rebuild` 输出 `result=unchanged`，不产生新版本。

### 11.3 APK 版本号规则

用户于 2026-09-22 要求把 APK 版本与更新记录清零，版本号从 **V1.0** 重新开始、每版 **+0.1**：

| | 规则 | 例 |
|---|---|---|
| `versionName` | 界面展示用，`V主版本.次版本`，每版 +0.1 | V1.0 → V1.1 → V1.2 |
| `versionCode` | `主版本 × 100 + 次版本 × 10` | V1.0=100、V1.1=110、V1.2=120、V2.0=200 |

- `versionCode` 必须**严格递增**：客户端 `ApkUpdatePolicy.decide` 只比较它
  （`manifest.versionCode <= 本机` 即视为无更新），Android 系统也不允许低版本覆盖安装。
  V1.0 取 100 而非 10，就是为了高于重置前的 42，已装 1.4x 的设备仍能收到 V1.0 的更新提示。
- 默认值写在两个 `app/build.gradle`（`android/`、`internal/mobile/`），也可用 `-PapkVersionCode=` /
  `-PapkVersionName=` 临时覆盖。后台「版本发布 → APK 更新」页会按当前公开清单自动预填下一版的 +0.1 / +10。
- 次版本满 9 后进主版本（V1.9 → V2.0，code 190 → 200），避免与 `×100 + ×10` 编码冲突。

### 11.4 Release 入口门槛（硬 fail fast）

Release 必须显式传入**纯 origin**（结尾斜杠会被 normalize 去掉），端点由 `/activate`、
`/hotupdate` 等固定路径拼接：

```bash
# 方式一：Gradle property
./gradlew assembleRelease -PapiBaseUrl=https://<正式域名>
# 方式二：统一环境变量
export OTV_RELEASE_API_BASE_URL=https://<正式域名>
./gradlew assembleRelease
```

规则与报错文案在两套工程里**逐字节相同**，对称性由
`tools/tests/test_release_api_origin_contract.py` 断言，改动必须同步两处。

- **拒绝**：IP 字面量（除已 opt-in 的自建 VPS）、http、userinfo、query、fragment、任何路径。
- **迁移 CA + IP 入口默认只允许 Debug 本机联调**，正式包一律拒绝。
- **无正式域名时的显式双重 opt-in**：`-PallowIpReleaseOrigin=true`
  （或 `OTV_ALLOW_IP_RELEASE_ORIGIN=true`）**且** `apiBaseUrl` 恰好等于
  `https://103.236.97.137:35208`。此时才把 `src/ipRelease/res` 挂进 release 变体，
  由同名资源为**这一个 IP** 信任迁移 CA（`@raw/mytv_migration_ca`），其余域名仍只信任系统 CA；
  带路径的 IP 入口 opt-in 不豁免。
- 正式包的网络安全配置只信任系统 CA，迁移 CA 只留在 `src/debug/res/xml/network_security_config.xml`
  与 `src/ipRelease/res` 供本机联调。
- 内测版（neice flavor）：`./gradlew assembleNeiceRelease`（无卡密 / 热更门控）。
- 签名共用 `optimaltv-release.keystore`（10 年）；不混淆（Chaquopy + 反射保守）。

## 12. 发布流水线

1. 修改 `tools/backend-src/`。
2. 跑后端与契约测试（§13.1）。
3. `python tools/build_backend_zip.py`（同时更新 TV 和移动版 assets 中的 `python-backend.zip`）。
4. 本机起后端完成接口冒烟 + **浏览器**验证网页功能。
5. `python tools/release_all.py --deploy`：先跑 `schema-migrations` 一次性迁移容器
   （成功后才 `up -d --build`，迁移失败阻止 API 启动），再部署 `web-api`
   （会先刷新豆瓣快照，再重建云端包与 App 内嵌 zip），并顺带重生成首装离线目录种子
   `assets/catalog_seed.json`（`tools/build_catalog_seed.py`；字段口径与
   `VodRepository.decodeSnapshot` 一致）。**种子只影响 APK、不进热更包，所以刷种子后必须重打 APK，
   但不用发新热更版本。**
6. 重打两个 APK（各跑一次 `.\gradlew.bat assembleRelease` + 入口门槛参数）。
   **必须在第 5 步之后**——否则 APK 内嵌 zip 与刷新过快照的构建产物不一致。
7. 上传并发布热更：
   `node 后台管理系统/scripts/ops/hu-upload.mjs --site "https://<站点>" --name "…" --notes "…"`
   （站点最高版本 +1、立即发布）。**`--site` 或 `SITE_URL` 必须显式传入**：
   缺站点直接 `exit 2` 失败，避免标准发布流程把热更静默发回已下线的云端。
   **必须直连自建 VPS**（云端后台桥读上游超时 30s，而 40MB 分片重组必然超时 502），
   并给 Node 指定迁移 CA：`NODE_EXTRA_CA_CERTS=android/app/src/main/res/raw/mytv_migration_ca.pem`。
8. 发布 APK 更新清单（`apk-publisher` 一次性容器，见 §14.1）。
9. 发布后自检：线上 `/web/` 的内容寻址 `assets/app.<hash>.js` 与 `tools/backend-src/www/app.js`
   的 SHA-256 一致；线上热更包 sha256 与本地 zip 一致；两个 APK 内嵌 zip 的
   `proxy.py` / `douban_catalog.py` / `douban_snapshot.json` / `www/app.js` 与
   `tools/backend-src` 逐一一致；`aapt2 dump badging` 确认 versionCode/versionName；
   `apksigner verify --print-certs` 确认两端签名证书一致；容器 healthy。

### 14.3 排障速查（三个 404 是探测方式错误，不是故障）

| 现象 | 根因 | 正确做法 |
|---|---|---|
| SSH 用 22 报 `AuthenticationException` | NAT 外部端口是 **55560** | 用 55560；别误判成密码错 |
| `/v1/storages/object/hotupdate/` 404 | `storage_service.py:37` 拒绝空 key | 带完整 key：`…/hotupdate/backend-hu23.zip` |
| 裸 `/hotupdate` 404 | 裸路径无 handler，需子路径 | 用 `/hotupdate/manifest`、`/hotupdate/check`、`/hotupdate/announce` |
| 登录成功后又弹登录框 | 会话密钥随机兜底导致多实例签名不一致 | 用固定派生密钥（`/run/secrets/admin-session-secret`） |
| 后台「备注编辑」保存失败 | 只部署了代码、没执行 SQL 迁移 | `release_all.py --deploy` 会先跑 `schema-migrations`；迁移文件全幂等 |
| 热更上传 502 `upstream_unavailable` | 云端后台桥读上游超时 30s，40MB 分片重组必超时 | **直连自建 VPS** + `NODE_EXTRA_CA_CERTS=…` |
| `publish_apk_update.py` 报 `ModuleNotFoundError: db_import` | VPS 上是旧副本，还在 import 已删除的云端路径 | 同步本地最新版（改走自建栈 `runtime_client`）到 VPS；备份旧文件 |
| 后台页能打开，但某个 tab 报 `permission denied for function xxx` | PostgREST 在进入函数体**之前**先查连接角色的 `EXECUTE`；函数体里的 `auth.uid()` 白名单只在调用后才生效 | 跑 `schema-migrations`（含 `rpc_grants_repair.sql`）；用 `admin_smoke.py` 验证，不要只看页面能否打开 |
| 后台「激活流水」页空白或报 `could not find function admin_logs` | `h_logs` 还在调云端 `admin_logs`，自建库只有 `admin_license_v2_log_export` | 已修：改走 `admin_license_v2_log_export`，按码过滤在服务端做 |

| `schema-migrations` 报 `refusing to replay historical migrations` | 账本为空，但硬失败清单要求的某个对象缺失，校验拒绝执行、缺失对象又永远补不上 | 已修：把可幂等重建的对象（IPTV 发布锁）移出硬失败清单，交给 pending 路径安装 |
| `schema-migrations` 报 `syntax error at or near ":"` / `column "f" does not exist` | psql 的 `\gset` 对 boolean 展开成裸的 `t`/`f`，`WHERE :var` 不是合法 SQL | 已修：探针结果按**文本**读出（`AS …_text \gset`），使用时写成 `:'var' = 'true'` |

## 15. 已知限制与风险

### 15.1 片源与出口限制（当前最大的未闭环项）

- **网页版片源覆盖取决于索引新旧**：VPS 出网访问 macCMS 系片源站（`www.hongniuzy2.com`、
  `www.haohankan.com`、`bfzyapi.com` 等）IPv4/IPv6 全部连接超时，服务器侧实时匹配必为空。
  主兜底是 §14.2 的本机静态索引。代价是：① 新片 / 冷门片要等下一次重建索引才有线路；
  ② 索引默认 30 天过期。**App 端不受影响**——设备取源在**本机网络**实时完成
  （`EmbeddedBackend` 起 `proxy.py`，`baseUrl=127.0.0.1`）。
- **VPS 也够不着部分视频 CDN**：片源分片（如 `hnts.ymuuy.com:65`、`c.baisiweiting.com:18443`）
  在 VPS 上超时，中继会 499。网页播放已改为「浏览器直连优先、失败回中继」绕开；
  但**纯 http 直链仍只能走中继**，这类片源在网页版会失败（App 端不受影响）。
- **「N 条合格线路」≠「N 部可播」**：那是 API 匹配评分的结果。猫眼媒体主机从 VPS 拉流本身不稳定
  （三次里两次 20~25s 超时），所以服务器代拉这条路受上游限制。平板 / 手机 App 走设备自己的网络，
  不受这个影响——平板能正常看与「VPS 出口访问第三方片源 API 失败」并不矛盾：
  后者说的是 VPS 出口，不是 App 不可用。
- 直播、搜索、目录、元数据接口不受上述问题影响，已在 VPS 上实测通过
  （直播源多在国内 IPTV 主机，VPS 可达）。
- **网页版播放尚未完成浏览器出画验收**：点播放会弹会员激活，网页的换线选择逻辑目前只有
  Node harness 层面的验证，没有真实浏览器出画证据。

### 15.2 其他边界

- 热更只覆盖内嵌后端；APK 级改动必须发版。设备端下载失败不重试（下次启动再来）；
  同版本号重发无法触达已隔离设备。
- `hotupdate_check` 是公开 RPC：最多泄露已发布包元数据（本就是公开分发物）；report 可被灌垃圾日志
  （detail 截 500 字符，量级异常用 `OTV_HU_OFF` 止血）。
- 网页版云端片库与 App 不完全一致（hhkan 对数据中心 IP 封锁 → macCMS 降级链，契约一致；
  分类树少「短剧」、无地区 / 年份筛选 → 前端隐藏）。
- 冻结判定对 libVLC 兜底引擎只记日志、不触发恢复（libVLC 不提供解码器计数，位置推进与

- 正式域名与公共 CA 证书尚未取得；当前正式包用 §11.4 的 IP + 迁移 CA 双重 opt-in 方案。

## 16. 合规与安全边界

### 16.1 影视源合规边界

当前配置的影视源均属于无授权聚合 / 采集类站点，项目没有取得其内容授权。
技术上的多源兜底、测速和中继只解决可用性，不构成法律豁免。

- 影视源可用性由测速和失败降权机制维护；来源或域名变化时重新评估。
- 个人 / 家庭自用的传播风险相对较低但不为零；公开分发、持续收费或对无授权内容收费会显著放大风险。
- 如转为公开产品，应替换为已授权内容源，并重新评估卡密收费与公网访问面。
- 第三方队标、海报和素材应记录来源与授权边界，不能因「非商用」自动推断为无限制使用。

### 16.2 安全边界

- 私钥、卡密 CSV、服务密钥、Cookie 和长期令牌不得进入 Git、云端部署包或文档。
- 播放源和第三方素材必须记录来源与授权边界；非商业素材不能默认推断为可商业使用。
- 变更公网接口、RLS、后台权限或热更新校验时，必须增加对应契约测试并记录回滚方式。
