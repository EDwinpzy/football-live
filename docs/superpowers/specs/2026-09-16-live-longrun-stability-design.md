# 直播长跑稳定性：体检取证 + 窗口自适应目标延迟 + 僵尸源换线

日期：2026-09-16
范围：TV 版与移动版共享播放层（`android/`、`internal/mobile/`）
状态：已实现，模拟器长跑验证中（证据见 `docs/04-records/测试记录.md`）

---

## 1. 用户问题

1. 足球直播 / 影视直播 / 影视点播**播一段时间（十几到二十分钟）后画面冻住不动**，
   退出 App 重进（甚至重启投影仪）后才能继续看；
2. 要求连续看一小时不出现卡顿；
3. 明确否掉了「卡死就自动重启 App」的硬兜底方案，只接受**取证 + 有限自愈**。

---

## 2. 现场证据（模拟器长跑实测）

### 2.1 供给侧是健康的

从内置中继日志逐条统计分片请求（2026-09-16 05:56–06:06，足球直播）：

| 指标 | 数值 |
|---|---|
| 分片请求总数 | 294（含少量重试重复） |
| 覆盖序号 | #1589 → #1860（271 个唯一分片） |
| 平均间隔 | 2.03s/片（与上游 2.013s 分片时长一致） |
| 序号跳号 | 0 |
| 请求间隔 > 4s 的空洞 | 0 |

结论：**中继与 CDN 没有断供**，卡顿不是「取不到分片」，而是播放器侧行为。

### 2.2 直播窗口只有 6 秒，而播放器被要求落后 15 秒

抓取上游媒体清单（经内置中继）：

```text
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-ALLOW-CACHE:NO
#EXT-X-MEDIA-SEQUENCE:1823
#EXT-X-TARGETDURATION:3
#EXTINF:2.013,  ...-1823.ts
#EXTINF:2.013,  ...-1824.ts
#EXTINF:2.013,  ...-1825.ts
```

3 段 × 2.013s ≈ **6.0s 可播放窗口**；而 `Engines.kt` 的 v1.23 修复把直播目标延迟统一
设为 `targetOffsetMs=15_000 / min=8_000 / max=30_000`。

目标偏移根本**不可达**：ExoPlayer 的速度控制会长期按 0.97x 追赶一个够不到的偏移，
播放位置相对实时持续漂移，直到被滑动窗口甩到最老分片之外。日志里的直接痕迹：

- `[HEALTH] 起播 … pos=-2s dur=6s`——位置被夹到窗口起点（负偏移）；
- `recovery kind=LIVE step=0 action=REFRESH_CURRENT reason=BUFFERING 8s 无进展 pos=1000`。

### 2.3 「僵尸源」把同线重试配额无限刷新

实测某备用足球信号源「能出画面、几秒后必断」：

```text
line fail(1): … ERROR_CODE_IO_NETWORK_CONNECTION_FAILED → 同线 fresh 重解析（1/3，不换线）
（5 秒后）READY line=1 → sameLineRetries 归零
line fail(1): … → 同线 fresh 重解析（1/3，不换线）   ← 永远停在 1/3
```

`onSessionStarted()` 里 `sameLineRetries = 0`（起播成功即恢复配额）与「短暂 READY」叠加，
导致配额永远用不完：App 死守一条死源循环，`engine rebuffer` 计数一路涨到 **400+**，
用户观感就是「一直卡，退出重进才好」。

## 3. 实施的修复

### 3.1 长时体检与冻结取证（`playback/PlaybackHealthLog.kt`）

- 播放会话每 **10s** 采样一次（`viewModelScope` 默认 Main 调度器——ExoPlayer 的
  `getVideoDecoderCounters()` 会校验应用线程，必须主线程取数）；
- 每 **5 分钟**打一行 `[HEALTH]`（按墙上时间计，跨会话重启不断档）：引擎/状态/位置/缓冲/
  渲染帧数/丢帧/解码器初始化/中继/后端探活/解密池/恢复阶梯/内存/线程/网络；
- 卡顿交给恢复阶梯前打一份多行 `PLAYBACK STALL DUMP`（对齐《15–20 分钟卡顿排查方案》§22）；
- **冻结判定**：`rendered` 帧数连续 30s 不增、而位置仍在前进（既有的两道看门狗只认
  「BUFFERING 超时」与「位置不前进」，对这种「时钟在走、画面不动」形态不响）→ 打
  `[STALL-DUMP]` 后交给**既有有限恢复阶梯**（刷新→换源→重建引擎→重置运行时；
  不含整机自重启，符合用户否决项）；
- 日志经 `OtvLog` 双写 logcat 与 `files/logs/otv.log`，重启 App 后仍能回看冻结前现场。

### 3.2 直播目标延迟按实测窗口自适应（`playback/Engines.kt`）

- `MediaEngine.setLiveWindowHintMs(windowMs)`：上层起播前探测清单窗口长度（所有
  `#EXTINF` 之和）并下发（0 = 未知，沿用旧档）；
- 窗口 ≤ 12s 视为「小窗口直播」：
  - 目标偏移取窗口的 40%（6s → 2.4s）、min 窗口/8、max 窗口×2/3 —— **可达**，
    等于把「延迟 2 秒」变成真正存在的抗抖动缓冲垫；
  - 缓冲档改 `min/max/起播/恢复 = 8s/16s/0.6s/1.5s`：恢复水位必须小于窗口，
    否则一次抖动就要等满整窗才出画（实测 6s 水位 + 6s 窗口 = 转圈 8s 后触发整会话重解析）；
- 窗口未知或大窗口（公网 IPTV 等）保持 v1.23 的 `15s/8s/30s`，行为不变；
- 档位变化时释放播放器实例，下次 `prepare()` 以新参数重建（不在播放中途重建）。

### 3.3 僵尸源换线（`ui/player/PlayerViewModel.kt`）

- 起播成功**不再**立即清零 `sameLineRetries`；
- 改由体检循环判定：**连续 60s 稳定出画**才恢复同线重试配额；
- 僵尸源撑不到 60s，第 4 次失败即走换线（而非无限同线重解析）。

## 4. 已知边界

- libVLC 兜底引擎不提供解码器计数（`frames=-1`），其 `buf=15000ms` 是引擎层占位值；
  冻结判定对 VLC 会话只记日志、不触发恢复（位置推进与 `[HEALTH]` 行仍可判断是否在播）；
- 小窗口直播的可延迟上限受上游窗口限制（6s 窗口最多缓冲约 4s）。要让直播更抗抖动，
  只能让中继把多段清单拼成更长窗口，属于后续可选项。
