# 片库筛选性能与准确度重构设计

## 背景

片库（「全部影视」页）的类型/地区/年份/评分/排序筛选，由内嵌后端 `douban_catalog.py` 提供，
TV、移动端、网页三端共用 `/vod/filters/{category}` 与 `/vod/show/{category}` 两个接口。

2026-09-18 实测（开发机 + 随包快照，`source=douban-snapshot`）：

1. **地区/年份没有真正交给豆瓣筛。** `_explore()` 把地区和年份拼进 `tags=`（`tags=电影,日本`），
   未使用豆瓣的 `countries=`/`year_range=` 参数；「更早」在实时路径上等价于不筛选（网页端直接把
   年份发成空串，`_explore()` 也忽略它）。
2. **本地兜底对「字段未知」放行。** `_matches()` 在条目缺少 `genres`/`regions`/`year` 时一律保留，
   实测：`show(variety, 任意筛选)` 返回 20 条、真实匹配 0 条；`show(anime, genre=剧情)` 返回 20 条、
   真实匹配 3 条。综艺与短剧的条目录从未补过类型/地区，于是「筛选等于没筛」。
3. **上游被封被当成「合法空结果」写进缓存。** 豆瓣对异常 IP 返回 HTTP 200 +
   `{"msg":"检测到有异常请求从您的IP发出…"}`（无 `data` 键），`_explore()` 按「无结果」处理，
   经 `_coalesced()` 以 `source=douban, stale=false` 写入 6 小时缓存 —— 界面空且锁死，恢复后也不刷新。
4. **筛选选项是写死的表**（电影 25 类型 / 18 地区），不是真实数据汇总。
5. **带筛选的请求逐条补详情。** 一次浏览最多 1+2 页上游 + 每页约 20 条详情抓取（并发 8、全局闸 16），
   冷缓存最多约 60 次上游请求。

约束（用户明确要求）：**不新增任何后台服务、第三方代理或第三方代码，APP 必须独立运行**；
片库筛选必须保持「豆瓣全站实时检索」这个标准。

## 目标

保持以豆瓣探索接口为准的全站实时检索，同时把准确度、性能与可靠性做到可验证：

- **准确**：任何筛选组合下，返回的每一条都能证明满足该组合。
- **不缩水**：上游可用时，结果来自豆瓣全站，而不是本地已抓取的子集。
- **快**：热缓存首屏 ≤ 100ms；冷缓存首屏 ≤ 2.5s；不再出现逐条补详情造成的秒级以上等待。
- **不假空**：上游不可用时绝不返回「没有内容」，也绝不让空结果锁死缓存。
- **独立**：全部在设备内嵌后端完成，无新增外部依赖。

## 设计

### 1. 上游调用按豆瓣语义传参

- `tags=` 只承载大类（电影/电视剧/动漫/综艺/短剧）。
- `genres=` 承载类型，`countries=` 承载地区，`year_range=` 承载年份，`range=` 承载评分，`start=` 承载分页。
- 年份映射：选中的当年 → `YYYY,YYYY`；「更早」→ `1,<当前年-11>`。
- **上游已经筛选过的维度，本地不再重复判定**，从结构上排除误杀。
- 参数用法属于接口事实，本仓库自行实现调用，不引入任何第三方库或源码。

### 2. 本地判定改为三态

对每个维度，条目的状态只允许是「匹配 / 不匹配 / 未知」；补位判定时**只有明确匹配才保留，未知一律剔除**。
判据优先级：列表行结构化字段 → 列表行 `card_subtitle` 解析结果 → （仅在必要时）详情接口。

取舍（已与用户确认）：**宁可少给，不给错**。上游不支持某维度的分类，结果数量会比豆瓣网页略保守。

### 3. 分类 × 参数能力矩阵数据化

- 新增一份随包发布的实测数据（每个分类支持哪些上游参数），由发布流程中的探测脚本生成。
- 代码按矩阵决定某维度「交给上游」还是「本地判定」，不把结论写进 `if` 分支。
- **不采信代码注释，只采信实测**：现有注释称「电视剧传 `genres=` 返回空页」，
  但 2026-09-18 的线上记录显示 `/vod/show/tv?genre=古装` 正常返回，两者矛盾。

### 4. 上游不可用与降级链

- **判定**：响应缺少 `data` 键、含 `msg`、非 JSON、HTTP 非 200、超时 → 判为「上游不可用」，抛错。
- **禁止**：上游不可用的结果一律不得写入缓存。
- **回退顺序**：同筛选条件的最近一次成功结果（标记 `stale`）→ 随包快照中套用同一套筛选规则的条目 →
  空结果但标记为「上游不可用」。
- **自愈**：标记不可用后进入冷却（默认 60 秒，可配置），冷却到期允许一次真实回源试探，成功即恢复正常状态。
- **呈现**：三端共用同一组 `stale`/`source` 语义。「数据可能不是最新」与「暂时获取不到」是两种不同文案，
  后者不是「没有符合条件的内容」。

### 5. 分页与 has_more

- 只有确认存在下一页数据时才置 `has_more=true`；补页上限沿用现有 2 页。
- 结果去重并保持稳定排序，翻页不得出现重复或跳条。

### 6. 筛选项来源

类型/地区/年份/评分选项改为三层合并：豆瓣 `search_tags` 官方清单 + 随包快照实测汇总 + 内置兜底表，
目标是每个选项点了都有内容。

### 7. 三端一致

- 三端共用同一后端契约，前端不再各自打本地补丁（如网页端 `year === "更早" ? "" : year` 必须删除）。
- 本次范围仅限片库筛选，不动播放线路、详情页与直播。

## 非目标

- 不引入自建代理、公开镜像、Cloudflare Worker 或任何第三方在线服务。
- 不使用官方 App 的 frodo 接口凭据。
- 不改动播放源体系、详情页数据链路与直播功能。

## 验收

- **准确度**：抽样自检脚本对每个分类 × 每个筛选维度断言「返回的每一条都真实匹配」，输出 JSON 证据。
- **覆盖率**：上游可用时结果来自豆瓣全站，不缩水到本地目录。
- **性能**：记录冷/热缓存下各筛选组合的首屏耗时，达到第 2 节的目标值。
- **可靠性**：模拟上游空壳响应，断言不写缓存、不返回假空、冷却后恢复即正常。
- **回归**：`tools/backend-src/tests` 全量通过；Kotlin 侧 `assembleRelease` 编译通过。
- **端到端**：TV 模拟器截图 + 网页五视口截图，覆盖筛选路径。
- **发布**：按仓库既定收尾流程执行（`release_all.py --deploy` → 双 `assembleRelease` → 热更上传 →
  文档记录 → 提交并推送）。

## 风险

- 豆瓣随时可能调整参数语义 → 能力矩阵是数据文件，改数据即可改行为；探测脚本可重复执行。
- 设备所在网络被豆瓣拦截 → 只能降级、不能变出数据（已与用户确认，不接受代理兜底）。
- 上游不认类型参数的分类，类型筛选结果数量偏保守。
