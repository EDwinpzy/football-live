# CloudBase 全栈迁出设计

日期：2026-09-23  
状态：用户已批准，待实施

## 1. 目标与成功标准

把 My TV 目前依赖 CloudBase 的数据库、文件存储、管理后台、激活、热更新、电视源与网页服务迁到用户现有 VPS。第一阶段不扩容，使用已检查的 Ubuntu Server 24.04.1 x86_64 主机。迁移期间保持已安装 App 可用；新环境完成验证后再切换新客户端，CloudBase 暂时承担旧客户端兼容转发。

成功标准：

- 新服务器独立承载数据库、后台 API、激活、热更新、电视源与网页/API；日常业务数据和新上传文件不再写入 CloudBase。
- TV、移动版和网页版的激活、续期/校验、公告、热更新、影视源配置、电视源与 APK 更新流程符合现有协议。
- 旧版 App 继续通过原 CloudBase 地址获得兼容响应；新版本客户端可直接使用新服务器。
- 旧管理入口 `/admin/*` 在兼容期保留地址，但管理操作由 VPS 处理；CloudBase 不再作为第二写入端。
- 数据与对象迁移前后完成数量、对象大小及 SHA-256 核验；有可实际执行的回滚路径。
- CloudBase 退役前以请求观测证据确认旧版客户端不再依赖兼容入口。

## 2. 已确认约束与现状

- 目标机：Ubuntu Server 24.04.1 LTS、x86_64；约 4 GB RAM、29 GB 系统盘，检查时约 27 GB 可用。不扩容是本次设计约束。
- 网络按服务商 NAT 端口转发使用；不修改安全组。SSH 连接使用服务商分配的外部端口。新服务的公网入口还需确定端口映射与稳定 HTTPS 域名。
- CloudBase PostgreSQL 当前数据库约 14 MB；业务表包括 `licenses`、`activate_log`、`hotupdate_pkg`、`hotupdate_log`、`announcements`、电视源及影视源版本/草稿表。
- 当前公开文件桶对象合计约 393 MB（14 个对象，最大约 100.7 MB），主要由热更新包、电视源及 APK 更新资源组成。
- 源码已有后台容器构建文件 `tools/cloudrun-admin/Dockerfile`；激活与热更新分别是 Node.js HTTP 函数，网页/API 后端是 Python，电视源重建有定时函数。
- 多处现有数据库访问依赖 CloudBase 的 PostgREST/Auth/Storage 形态；SQL RPC 使用 `auth.uid()` 身份约束。直接换普通 PostgreSQL 或另一个托管产品不是透明替换，需要保留这些业务权限语义。
- 已发布 App 内含 CloudBase 激活、热更新与电视源地址；仅部署新服务器不会改变旧客户端的地址。
- CloudBase `otv-admin` 仍是启用中的管理入口；切换后若原代码继续运行，可能将管理操作写回旧库并形成第二写入端。
- 凭据、私钥和服务账号不得进入 Git、镜像或文档；目标机账户密码不写入本设计。

## 3. 方案比较与选择

### 方案 A：轻量自托管服务栈（推荐）

在 Docker Compose 中部署 PostgreSQL、API/业务服务、反向代理和本地文件服务。保留现有 SQL 业务函数的结果语义，由服务端受控 API 调用数据库；文件落在单独的数据目录，通过 HTTPS 静态下载提供 Range 支持。利用现有后台 Python 容器基础，逐个迁移 CloudBase 函数行为。

优点：组件少，适合当前 4 GB RAM / 29 GB 磁盘；数据与对象格式可直接掌控。代价：需要实现 CloudBase Auth/PostgREST/Storage 目前承担的接口边界，并重验权限。

### 方案 B：完整自托管 CloudBase 兼容平台

自建完整 Auth、PostgREST、Storage 及数据库组合，尽量保持现有访问方式。

优点：部分数据/RPC 调用形式相近。代价：身份字段、角色与 `auth.uid()` 语义不保证一致；组件和内存占用更多，在当前主机上余量较小，仍需适配与安全审计。

### 方案 C：CloudBase 长期保留为 API 网关

只迁数据库和文件，让 CloudBase 函数持续代理新服务器。

该方案过渡风险较低，但 CloudBase 仍是长期运行依赖，不满足整套服务迁出的目标，因此只用于迁移窗口，不作为最终形态。

**选择方案 A。**保留原 CloudBase API 地址的短期兼容代理；业务数据主写入切到新服务器后，不做双主写入。`otv-admin` 仅转发后台页面和 `/api/*`，新服务器登录门禁继续生效。

## 4. 目标结构

```text
已安装旧 App ──原 CloudBase 地址──> 临时兼容代理 ──> 新服务器 API
旧管理浏览器 ──CloudBase /admin────> 管理兼容代理 ──> VPS 管理后台
新 App / 网页 ──HTTPS 新域名──────> 新服务器反向代理
                                      ├── 管理后台 / 网页 API
                                      ├── 激活 / 热更新 / IPTV / VOD API
                                      ├── PostgreSQL
                                      └── 本地对象目录（公开文件支持 Range）
```

当前部署选择 VPS IP 与服务商 NAT 端口作为 HTTPS origin：`https://103.236.97.137:35208`，健康检查使用外部端口 `25182`。不配置安全组，也不改 NAT。此 HTTPS 证书由迁移 CA 签发，App 与 CloudBase 代理会显式信任；浏览器直连在 CloudBase 截止后需要先信任该 CA。

Compose 服务按内存预算配置重启策略与合理上限；不运行不必要的完整平台组件。所有持久化数据使用宿主机挂载目录，容器重建不丢数据。定时电视源任务迁为受控定时容器或宿主机 timer，确保单实例执行。

公网流量只经反向代理进入应用。管理接口保留认证、速率限制和日志；数据库仅在容器网络内监听。通过 NAT 映射提供 SSH 与 Web HTTPS 入口，不要求配置安全组。备份保存到另一台设备或异机存储，不与 VPS 单盘共因失效。

## 5. 迁移范围

### 数据库

- 依据现有 `tools/*_migration.sql` 汇总目标 PostgreSQL schema、索引、RPC 逻辑和必要角色。
- 将当前表数据与序列状态迁移到新库；重写/替代 `auth.uid()` 权限检查，保持只允许管理服务执行管理 RPC，公开端只执行明确开放的接口。
- 迁移卡密签发公钥/私钥关系时保持票据验签兼容；私钥只放在受限服务器密钥文件或秘密注入中。

### 文件存储

- 迁移热更新包、电视源 M3U、台标、APK 与更新清单。
- 保留历史热更新版本号及其状态；对象逐个核对长度和 SHA-256。
- 下载地址支持 HTTPS、匿名公开资源的既有语义及 Range/断点续传；上传只允许管理后台认证后执行。
- CloudBase 到期前，旧 App 的 API 调用由窄职责函数代理到 VPS；旧 APK 不信任迁移 CA，因此 APK 与热更新大文件继续镜像到 CloudBase 对象存储。云函数响应上限为 6 MB，不用于转发这些大文件。新 APK 使用 VPS 地址与内置迁移 CA。

### 业务 API

- 迁移管理后台、激活协议 v2、热更新检查/报告/下载、公告、影视源发布、电视源发布/回滚、APK 更新清单、网页和现有代理 API。
- 保持现有 JSON 字段、状态码/业务码、缓存与客户端节流约定；接口变更只通过新客户端版本引入。
- IPTV 定时重建任务与手动发布互斥，迁移后不得由旧任务覆盖新发布内容。

## 6. 分阶段上线与回滚

1. **备份与基线**：导出数据库结构/数据、迁移文件、运行环境变量名称清单和对象清单；保存 CloudBase 文件/数据库恢复点。备份不进入 Git。
2. **目标机基线**：确认 NAT 对外端口、稳定域名和 TLS 方案；设置 Docker/Compose、宿主机目录权限、日志轮转与远程备份。先验证磁盘和内存预算。
3. **并行搭建**：部署空服务，不接管线上流量；导入一份数据与对象，核对记录数、序列、哈希和接口契约。
4. **验收**：用 TV/移动 debug 包和浏览器逐条走激活/续期/恢复、热更新 Range 下载、公告、IPTV、VOD 配置、管理后台上传/发布/回滚及网页页面。
5. **切换新写入**：短暂停止管理写操作，做最终增量同步；新服务器成为唯一主写端。不得双写两套数据库。
6. **兼容期**：旧 CloudBase 函数保留为原地址的窄职责转发代理，包含 `activate`、`hotupdate`、`iptv` 和 `otv-admin`；新 APK/网页改指新地址。按旧端点访问日志观察旧客户端存量。
7. **退役**：确认旧客户端流量达到约定阈值并持续观察后，先关闭兼容代理进行可回滚验证；稳定后再清理 CloudBase 服务与数据。

发生错误时暂停新写入；若切换窗口尚未接受新写入，则将入口恢复到 CloudBase。若新端已有写入，先将新端变更导回 CloudBase 或保持新端为主并修复，不允许简单回切造成数据分叉。

## 7. 验收与监控

- 数据：关键表逐表计数、主键/序列核对、业务不变量（卡密状态、激活绑定、已发布最高热更/IPTV 版本）。
- 文件：对象数、大小、SHA-256；抽测公开 URL、权限、Range 断点续传。
- API：旧/新端协议样例对照；异常码、未授权访问、重放/并发激活、热更新停更开关、管理登录与会话。
- 运行：容器重启后数据仍在；服务器重启后自动恢复；内存、磁盘、请求失败率和备份任务可观测。
- 客户端：旧 APK 经 CloudBase 兼容代理正常；旧 `/admin` 入口的登录 Cookie 和管理 API 由 VPS 处理；新 APK 直连新端正常；电视/移动/网页版结果一致。

## 8. 迁移期限和后续处理

- CloudBase 环境预计于 2026-10-09 到期。旧环境到期后线上业务会停止；迁移版 APK 必须在该日期前发布并从旧客户端更新入口可下载。
- 本次阶段使用日期化的本地数据库与对象备份；完成迁移后再配置长期异机备份位置。
- CloudBase 兼容函数保留到环境服务截止；大文件镜像只保留至该截止日期。

本设计不包含线上切流、迁移数据写入或 CloudBase 退役操作；这些步骤在实施计划中逐项安排，并在维护窗口执行。
