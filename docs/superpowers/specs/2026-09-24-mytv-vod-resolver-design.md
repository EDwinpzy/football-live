# My TV 点播 Source Resolver 设计

日期：2026-09-24  
状态：待用户规格审核  
依据：桌面全链路优化方案及当前 web-api、metadata center、静态 vod-lines 索引和两套 Android VOD 实现。

## 1. 目标

降低用户选片到首条可信线路的延迟，避免单个源超时被误判为没有片源，并用近期成功线路与健康数据辅助排序和恢复。服务端负责调度与匹配；播放数据优先由客户端直连。

不扩展未经授权的来源，不绕过反爬或鉴权，不把低置信度近似标题当作有效线路。

## 2. 当前基础与差距

- tools/backend-src/vod_sources.py 已有并发搜索、首个结果提前返回、后台补充、进程内缓存、评分和熔断。
- vod_api.py 的 detail() 默认等待全部来源完成，抵消了早返回能力。
- 静态 vod-lines 索引以 Douban ID 为键；metadata center 同时提供内部 mytv_id 与 douban_id。
- Android 详情会再次强制刷新；空 episodes 可以直接变为 UNAVAILABLE。
- 两个 Android 工程共享的 VodRepository 有详情与播放 URL 缓存，但没有按影片/集记录的 last-good、健康排序或逐源首条有效线路流。

## 3. 身份映射与兼容

mytv_id 是客户端公开的规范主键。服务端通过 metadata center 的显式映射解析为 douban_id，再查询已有静态索引或当前启用的来源。索引带数据版本、来源 ID、内容 ID、集数映射和匹配分数。

映射缺失、冲突或置信度不足时，返回未匹配/继续补查状态，不猜测播放地址。现有 Douban ID 索引在迁移期间保留为可验证的回退数据，差异验收通过后再决定替换索引生产方式。

## 4. API 与返回语义

新增快速解析接口，语义为 GET /vod/resolve/{mytv_id}?episode=1，返回 mytv_id、episode、resolve_version、preferred、backups、cache 信息及状态。状态至少区分 RESOLVING、FAST_PATH_FAILED、FALLBACK_SEARCHING、STALE_AVAILABLE、TEMPORARILY_UNAVAILABLE 和 MATCHED。

接口先返回可信 preferred；后台可继续补齐 backups。客户端不能等待全部来源完成后才准备播放。

## 5. 匹配、缓存和健康策略

1. 查询 last-good、热缓存和预匹配索引。
2. 无命中时仅并行请求健康排序靠前的 3 个已配置来源。
3. 单源软超时 600–800ms，总快路径预算 1.2–1.5s。任一可信线路到达即返回；后台补查任务必须有边界、取消与异常收尾。
4. 第一波失败后才用片名、原名、别名、繁简、年份、类型、季/集和主演宽松匹配；最低可信分数有明确值和反例测试。
5. 成功缓存 30 分钟至 6 小时；健康排序缓存约 5 分钟；失败只缓存 15–60 秒并触发重试/后台刷新。空结果不得长期缓存。
6. 健康分综合 API 成功率、匹配成功率、首帧成功率、延迟、画质和最近成功时间。连续失败降权、退出快路径或短期熔断；恢复需至少两次探测成功。
7. 初版先复用现有 Postgres 与小型进程 LRU。只有服务器内存实测及并发基准证明容量足够、且多 worker 共享缓存有实际收益时才启用 Redis。

所有已配置来源均不可用时，UI 显示“线路暂不可用，可重试”。确实没有任何有效来源时不伪造播放线路。

## 6. 可观测性与隐私

解析记录包含匿名化影片 ID、来源 ID、缓存类型、候选数、耗时分段、匹配结果和错误类别。不得记录签名播放 URL、Cookie、卡密、完整授权头或个人身份信息。

服务指标包含请求数、p50/p95/p99、匹配/缓存命中率、来源超时/错误、熔断状态、metadata 版本和 5xx。

## 7. 验收

- 合同测试验证规范 ID、episode、preferred/backups、状态和版本字段。
- 竞速测试证明慢源不会拖延首个可信结果；超时、429、403、404、5xx、空结果和缓存过期都有覆盖。
- ID 映射的正例、缺失、歧义、重复和过期索引都有测试。
- 空结果只可短期缓存；回退搜索、任务取消/收尾和熔断恢复没有任务泄漏。
- 真实可测内容集首条片源目标 P50 ≤ 500ms、P95 ≤ 1.5s，匹配率目标至少 99%。未达到时报告基线、样本和失败来源，不能用模拟数据宣称通过。
- 常规视频流量不经服务器中继。
