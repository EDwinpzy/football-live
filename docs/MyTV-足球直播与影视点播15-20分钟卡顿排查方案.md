# My TV · 足球直播与影视点播 15–20 分钟卡顿排查方案

> 项目：My TV / OptimalTV  
> 适用端：TV 版、移动版；网页版可参考同一后端/HLS链路部分  
> 适用版本：当前 Media3 + 本机中继 + Chaquopy `:backend` 架构  
> 核心问题：足球直播、影视点播均存在“正常播放一段时间后，约 15–20 分钟卡住”的现象  
> 排查原则：**先定层，再修复；禁止看到 BUFFERING 就直接归因于线程阻塞。**

---

# 1. 排查目标

本次必须最终回答以下问题：

```text
1. 卡住时 UI 是否仍然响应？
2. Media3 当前处于 READY、BUFFERING、IDLE 还是 ERROR？
3. currentPosition 是否停止？
4. bufferedPosition 是否继续增长？
5. HLS playlist 是否仍持续刷新？
6. segment 是否仍持续下载？
7. HTTP 是否出现 401 / 403 / 404 / 410 / 5xx / timeout？
8. 当前真实播放 URL、Cookie、Token 是否已过期？
9. relay 是否完成续签/换源，但内部仍引用旧地址？
10. 重新解析同一播放源后是否立即恢复？
```

最终需要把问题归入以下某一层：

```text
A. 上游源生命周期
B. HLS / DASH playlist 与 segment
C. 本机 Relay / 中继
D. 后端解析与解密
E. Media3 Load / Buffer
F. MediaCodec / 时间戳
G. App 线程或资源泄漏
H. 网络/CDN
```

---

# 2. 总体优先级

如果“足球直播”和“影视点播”都存在接近 15–20 分钟的定时卡顿，优先级调整为：

| 优先级 | 怀疑点 | 原因 |
|---|---|---|
| P0 | 共用 Media3 / Relay 生命周期逻辑 | 两类业务都复现，说明共用层嫌疑上升 |
| P0 | URL / Token / Cookie 过期 | 固定时间窗口最典型 |
| P0 | HLS playlist / segment 地址缓存错误 | 直播和点播 HLS 都可能中招 |
| P1 | Media3 BUFFERING 后恢复策略失效 | 共用播放器层 |
| P1 | HTTP 连接池 / 请求超时 / CDN 长连接 | 长时间播放后共同触发 |
| P1 | `engineEpoch` / session 代数管理问题 | 共用播放会话 |
| P2 | MediaCodec / 时间戳 discontinuity | 依赖具体媒体文件 |
| P2 | WebView/QuickJS 解密池 | 更偏足球解析阶段，不足以解释所有点播 |
| P3 | Compose 主线程阻塞 | 如果 UI 正常响应，则基本排除 |

# 6. 足球直播排查方案

## 6.1 当前链路

```text
比赛
↓
/api/stream
↓
频道页 / 播放器页
↓
QuickJS / WebView / 云端解密
↓
真实播放地址
↓
本机 HLS Relay
↓
Media3
```

项目已有：

```text
签名约 9 分钟轮换
提前约 90 秒续签
热切换 upstream
```

因此足球优先怀疑 URL 生命周期。

---

## 6.2 足球实验 A：卡住后切换信号源

步骤：

```text
1. 进入比赛
2. 记录起播时间
3. 播到卡住
4. 不退出播放页
5. 手动切 B 信号源
```

### 如果 B 立即恢复

说明：

```text
Media3 主体可用
UI 可用
设备网络大概率正常
```

优先指向：

```text
A 源 Token 过期
A 源 playlist 停止刷新
A relay session 失效
```

---

## 6.3 足球实验 B：重新进入同一比赛

```text
卡住
↓
退出播放页
↓
重新进入
↓
重新解析同一信号
```

如果立即恢复：

```text
旧播放地址失效概率极高
```

如果重新进入后又能稳定播约相同时间：

```text
基本锁定 TTL / Token 生命周期问题
```

---

## 6.4 足球实验 C：验证 9 分钟续签

必须记录：

```text
relayCreatedAt
renewScheduledAt
renewStartedAt
renewFinishedAt
oldUrlHash
newUrlHash
oldHost
newHost
```

示例：

```text
OTV-RELAY renew_start age=7m31s old=aaa111
OTV-RELAY renew_success age=7m32s old=aaa111 new=bbb222
```

之后检查实际媒体请求。

如果出现：

```text
renew_success new=bbb222
```

但后续：

```text
PLAYLIST/SEGMENT 仍持续请求 aaa111
```

结论：

```text
续签成功，但实际 relay pipeline 没有切到新 upstream。
```

---

## 6.5 足球重点检查：变量捕获

特别检查类似：

```kotlin
val upstreamUrl = session.upstreamUrl

launch {
    while (...) {
        request(upstreamUrl)
    }
}
```

如果续签只是：

```kotlin
session.upstreamUrl = newUrl
```

旧 coroutine 仍使用旧的：

```text
upstreamUrl
```

应改成每轮读取最新状态，或者取消旧任务重建。

---

## 6.6 足球重点检查：相对路径重写

不要只换：

```text
master.m3u8
```

还要检查：

```text
media playlist
.ts
.m4s
EXT-X-KEY
EXT-X-MAP
子 playlist
音轨 playlist
字幕 playlist
```

常见事故：

```text
master 已换新 Token
segment 仍然带旧 Token
```

最终在 buffer 用尽后卡住。

# 7. 影视点播排查方案

影视点播同样出现 15–20 分钟卡顿时，要与足球区别处理。

当前点播来源：

```text
hhkan 主详情
+
MacCMS 补充池
  bfzy
  fdzys
  暴风
  极速
  金鹰
  虎牙
  豪华
  红牛
  速播
  360
```

播放仍经过共用：

```text
PlayerViewModel
↓
Media3
↓
必要时 relay HLS
↓
libVLC fallback
```

因此点播首先判断：

```text
是某一站卡
还是所有影视源都卡
```

这是最重要的分叉。

---

# 8. 影视实验 A：同一影片换线路

选择一个能稳定复现的影片/集数。

步骤：

```text
线路 A 播放
↓
约 15–20 分钟卡住
↓
立即切线路 B
```

记录：

```text
A 站点
A URL hash
B 站点
B URL hash
```

### A 卡，B 正常

优先判断：

```text
单站播放地址生命周期问题
CDN 问题
该站 playlist 问题
该站 segment 问题
```

### A、B、C 都会在类似时长卡

优先判断：

```text
共用 Media3
共用 relay
HTTP client
播放器 session
设备解码
```

---

# 9. 影视实验 B：同一线路重新解析

不要直接复用原 URL。

步骤：

```text
线路 A 播 18 分钟卡住
↓
退出详情
↓
重新进入
↓
重新请求详情/线路
↓
重新解析线路 A
```

如果马上恢复：

```text
旧播放 URL 有生命周期
```

如果新 URL hash 与旧 URL hash 不同：

```text
证据非常强
```

如果新旧 URL 完全相同但重新播放恢复：

优先查：

```text
Media3 状态
HTTP connection
relay session
播放器资源释放
```

---

# 10. 影视实验 C：直接保存真实 m3u8 做对照

对于 HLS 点播源，首次解析时记录真实：

```text
master.m3u8
media.m3u8
```

注意日志里不要存完整敏感 Token，可以测试环境单独保存。

在开发机上做两个实验。

### 实验 1

起播后立即请求：

```text
m3u8 → 200
segment → 200
```

### 实验 2

等待约 20 分钟后再次请求同一 URL：

如果变为：

```text
401
403
404
410
```

则可直接确认：

```text
点播真实地址存在 TTL。
```

---

# 11. 影视实验 D：判断是否与集数/文件时间轴有关

选择不同类型：

```text
电影
45 分钟电视剧
20 分钟短剧
```

观察故障是：

```text
播放开始后固定约 18 分钟
```

还是：

```text
总在某个媒体时间点，例如 00:18:37
```

这两个含义不同。

### 固定“播放时长”发生

例如每次：

```text
起播后约 18 分钟
```

优先：

```text
Token
Cookie
session TTL
HTTP 生命周期
```

### 固定“媒体时间点”发生

例如无论从头播还是 seek，都会在：

```text
00:18:37
```

卡住。

优先：

```text
坏 segment
PTS/DTS 跳变
EXT-X-DISCONTINUITY
编码异常
音轨异常
文件损坏
```

这个实验非常重要。

---

# 12. 影视实验 E：Seek 穿越故障点

假设一集总在：

```text
00:18:30
```

卡住。

重新进入后：

```text
直接 seek 到 00:19:30
```

### 能继续播放

说明：

```text
18:30 附近 segment / 时间戳异常
```

### 依然在起播 15–20 分钟后卡

说明：

```text
生命周期问题
```

而不是固定媒体文件坏点。

---

# 13. 影视实验 F：Media3 与 VLC 对照

当前项目已有：

```text
Media3 → relay → libVLC
```

对同一真实地址强制两种播放器。

### Media3 卡，VLC 正常

重点检查：

```text
Media3 LoadControl
Media3 HLS playlist tracker
Media3 HTTP DataSource
MediaCodec
Media3 时间戳容错
```

### Media3 和 VLC 都卡

重点检查：

```text
上游 URL
CDN
Token
relay
真实媒体文件
```

这可以快速把“播放器问题”和“源问题”分开。

# 14. HLS 点播专项检查

影视点播里如果是 HLS，必须重点检查以下标签：

```text
#EXT-X-ENDLIST
#EXT-X-KEY
#EXT-X-MAP
#EXT-X-DISCONTINUITY
#EXT-X-BYTERANGE
#EXT-X-PROGRAM-DATE-TIME
```

重点检查：

### 14.1 AES Key

如果：

```text
#EXT-X-KEY:METHOD=AES-128,URI="..."
```

Key URL 可能自己也有 Token。

可能出现：

```text
m3u8 仍然 200
segment 仍然 200
KEY 403
```

播放器表现仍然是卡住。

所以日志必须单独区分：

```text
KEY
```

---

## 14.2 fMP4 init segment

对于：

```text
.m4s
```

检查：

```text
#EXT-X-MAP
```

如果 init segment 失效，同样可能造成解码停止。

---

## 14.3 discontinuity

如果故障总发生在特定位置，检查：

```text
#EXT-X-DISCONTINUITY
```

前后是否发生：

```text
codec 改变
分辨率改变
音轨改变
PTS 重置
```

---

# 15. 非 HLS 点播专项检查

如果源直接返回：

```text
.mp4
.mkv
.flv
```

重点看是否支持：

```text
Accept-Ranges: bytes
206 Partial Content
```

检查：

```text
Range 请求
Content-Range
Content-Length
```

如果服务器中途关闭连接，而 Media3 重连 Range 请求失败：

可能表现为：

```text
播十几分钟后卡死
```

日志需要记录：

```text
requestedRangeStart
HTTP 206/200
Content-Range
```

常见错误：

```text
第一次 GET = 200
重连 Range = 服务端仍返回 200 全文件
```

或：

```text
Range = 403
```

# 16. Media3 共用层专项排查

如果足球 + 影视都卡，重点检查这里。

---

## 16.1 BUFFERING 看门狗

卡顿时记录：

```text
BUFFERING start time
BUFFERING duration
bufferedPosition
network request count
```

分类：

### 类型 1

```text
BUFFERING
bufferedPosition == currentPosition
网络 403
```

结论：

```text
源失效
```

### 类型 2

```text
BUFFERING
bufferedPosition == currentPosition
网络没有任何新请求
```

结论：

```text
Loader / playlist tracker / relay 卡死
```

### 类型 3

```text
READY
bufferedPosition 大幅领先
position 不动
```

结论：

```text
解码/渲染/时钟问题
```

# 17. MediaCodec 专项判定

卡住时如果：

```text
bufferedPosition 继续增长
HTTP 持续 200
Media3 仍 READY
currentPosition 停止
```

重点检查：

```text
MediaCodecVideoRenderer
MediaCodecAudioRenderer
DecoderInitializationException
CodecException
```

同时记录：

```text
decoder name
mime type
resolution
audio codec
```

如果切 VLC 立即恢复：

```text
优先归 MediaCodec / Media3 decoder
```

---

# 18. engineEpoch / 播放会话检查

项目存在：

```text
engineEpoch
```

必须确认：

```text
旧 session 的 coroutine
旧 retry task
旧 relay callback
旧 player listener
```

不会在新 session 建立后继续工作。

重点检查：

```text
epoch != currentEpoch
```

是否全部立即退出。

否则可能发生：

```text
旧续签任务
↓
18 分钟后触发
↓
覆盖当前 URL
↓
播放器突然回到失效地址
```

这种问题尤其容易表现为“播放一段时间后突然卡”。

---

# 19. HTTP Client / 连接池检查

如果不同站点都约 15–20 分钟后失败，检查：

```text
OkHttp connectionPool
readTimeout
callTimeout
DNS
HTTP/2
keep-alive
```

开发测试可以做 AB：

```text
A：当前连接池
B：每次新建连接 / Connection: close（仅测试）
```

如果 B 不再复现：

重点查：

```text
连接复用
HTTP/2 stream
服务器 keep-alive
代理连接
```

注意：

```text
不要把 Connection: close 当正式修复
```

它只用于定位。

# 20. Relay 专项检查

如果点播和足球都经过同一个 relay，这是最高优先级之一。

每个 relay session 记录：

```text
relaySessionId
createdAt
lastPlaylistAt
lastSegmentAt
upstreamUrlHash
upstreamGeneration
requestCount
errorCount
```

卡住时输出快照：

```text
OTV-RELAY-DUMP
```

必须能看出：

```text
Media3 是否还在请求 localhost
relay 是否还在收到请求
relay 是否还在请求 upstream
upstream 返回什么
```

形成四段：

```text
Media3
↓
127.0.0.1 relay
↓
remote host
↓
CDN
```

定位哪一段断了。

# 23. 卡顿恢复策略建议

在定位前，不建议直接大改。

但可以增加保守恢复机制。

---

## 23.1 足球

如果：

```text
BUFFERING > 5–8s
```

同时：

```text
playlist / segment 401、403、404、410
```

执行：

```text
重新 /api/stream
↓
重新解密
↓
拿新 URL
↓
保持当前播放 UI
↓
重建 relay / MediaItem
```

直播无需恢复精确 position，只追当前 live edge。

---

## 23.2 点播

如果确认 URL TTL：

```text
记录 currentPosition
↓
重新解析同一线路/同一集
↓
拿新 URL
↓
重新 prepare
↓
seekTo(oldPosition)
↓
继续播放
```

建议减去少量：

```text
1–3 秒
```

避免落到失效 segment 边界。

---

## 23.3 不要无限重试

单次 stall 最大：

```text
自动刷新 1 次
同线路重试 1 次
切备线 1 次
```

之后才：

```text
Media3 → relay → VLC
```

避免形成后台死循环。

---

# 24. 推荐排查顺序

严格按以下顺序。

## P0：当天完成

```text
1. 足球卡住后切源测试
2. 足球退出重进测试
3. 影视同片换线路测试
4. 影视同线路重新解析测试
5. 确认 UI 卡住时是否仍响应
```

---

## P1：加日志

```text
6. Media3 状态日志
7. HTTP playlist/segment/key 日志
8. relay session 日志
9. renew old/new URL hash
10. engineEpoch 日志
```

---

## P2：做 AB

# 25. 最终判定矩阵

| 现象 | 最可能原因 |
|---|---|
| 卡住后切源立即恢复 | 当前源失效 |
| 退出重进同源立即恢复 | URL / Token TTL |
| 新解析 URL hash 改变后恢复 | URL 生命周期 |
| 旧 URL 20 分钟后返回 403 | Token 过期，已确认 |
| playlist 200、segment 403 | segment 鉴权过期 |
| playlist/segment 200、KEY 403 | AES Key URL 过期 |
| renew 成功但仍请求旧 hash | relay 热切换 bug |
| 多个影视站都相同时长卡 | 共用播放器/relay |
| 同一影片固定时间点卡 | 媒体文件 / segment / PTS |
| seek 越过故障点可播 | 媒体坏点 |
| Media3 卡、VLC 正常 | Media3/Codec |
| Media3/VLC 都卡 | 上游/relay/CDN |
| bufferedPosition 增长但画面不动 | decoder / renderer |
| BUFFERING 且无网络请求 | Loader / relay pipeline 卡死 |
| App UI 也完全无响应 | 主线程/死锁/ANR |

# 26. 当前最值得优先验证的两个假设

## 假设 A：共用播放地址生命周期问题

因为足球和影视都出现类似时间窗口：

```text
正常
↓
15–20 分钟
↓
卡住
```

首先确认是否存在：

```text
Token TTL
Cookie TTL
临时签名 TTL
CDN URL TTL
```

这是最高价值实验。

---

## 假设 B：共用 Relay / Media3 长时间会话问题

如果：

```text
多个完全不同站点
不同域名
不同影片
足球也一样
```

都在类似时长发生，则不能继续只查源站。

应把最高优先级移动到：

```text
Relay session
Media3 Loader
engineEpoch
HTTP connection reuse
```

# 27. 验收标准

问题不能以“感觉不卡了”验收。

至少完成：

```text
足球：
连续播放 ≥ 90 分钟 × 3 场

影视 HLS：
连续播放 ≥ 90 分钟 × 3 个不同源

影视 MP4/其他：
连续播放 ≥ 60 分钟 × 2 个源

切源：
故障恢复 ≥ 10 次

前后台：
进入后台 2 分钟后回来继续播放

网络：
Wi-Fi 短断 5–10 秒后恢复
```

要求：

```text
无永久 BUFFERING
无必须退出 App 才能恢复
无旧 session 覆盖新 session
无持续 401/403 后无限重试
```

# 30. 最短执行版

如果只做最关键的排查，按这个顺序：

```text
① 足球卡住 → 切源

⑨ relay / 直连对照
⑩ 最后才查线程、Codec、内存
```

若第 ⑤ 或第 ⑦ 命中，基本就能直接进入修复阶段。
